# Space Adventure — контекст для продолжения работы

Этот файл — конспект для Claude (или любого другого агента), который продолжит работу над
проектом на другой машине/аккаунте без доступа к истории текущей сессии. Дизайн-документ
(`game_design.md`) и архитектурные заметки (`architecture.md`) остаются основным источником
истины по геймплею; этот файл — про то, что уже сделано и как с этим работать.

## Что это за проект

Кооперативная 2D top-down игра про экипаж корабля (Barotrauma / Pulsar: Lost Colony / FTL).
C# / .NET 9 / MonoGame (WindowsDX). Клиент-серверная архитектура с первого дня: соло-игра —
это клиент, который в фоновом потоке поднимает встроенный сервер и общается с ним через
in-process транспорт (`InProcessTransport`), но серверная симуляция ничего не знает про то,
что клиент "локальный" — при необходимости транспорт заменяется на реальную сеть без переписывания
модели.

## Структура решения

```
Space adventure/
  game_design.md       — дизайн-документ (источник истины по геймплею, фазы 1-4)
  architecture.md       — архитектурные заметки/открытые вопросы
  SpaceAdventure.sln
  src/
    SpaceAdventure.Shared/    — модель данных + протокол, без MonoGame-зависимостей
    SpaceAdventure.Server/    — вся симуляция (World.cs + partial-файлы по темам)
    SpaceAdventure.Client/    — рендер/ввод, никакой игровой логики
    SpaceAdventure.Tests/     — ручной test runner (без внешнего фреймворка), TestRunner.cs
```

### Сборка / тесты / запуск

```bash
dotnet build "SpaceAdventure.sln"
dotnet run --project src/SpaceAdventure.Tests --no-build     # 106/106 должно быть зелёным
dotnet run --project src/SpaceAdventure.Client --no-build    # запускает окно игры (Windows-приложение);
                                                              # первым делом покажет экран выбора корабля (1/2/3)
```

Если `dotnet build` зависает — это почти всегда NuGet-рестор для `dotnet-mgcb` (Content Pipeline)
в песочнице без сети. Решение: включить реальный доступ к сети для команды сборки (в Claude Code
это `dangerouslyDisableSandbox: true` у Bash-тула). После первого успешного восстановления пакет
кэшируется и дальше собирается офлайн без проблем.

## Конвенции проекта (важно соблюдать)

- **Файлы держим маленькими.** Как только класс разрастается на несколько обязанностей — делим
  на `partial class` по темам. Пример: `World.cs` (ядро) + `World.Movement.cs` + `World.Combat.cs`
  + `World.Interact.cs` + `World.Voyage.cs` + `World.EnemyAi.cs` + `World.Atmosphere.cs` +
  `World.Reactor.cs`.
- **Shared = только данные** (records, enums, простая геометрия/математика). **Server = вся логика**.
  **Client = только рендер и перевод ввода в команды**, никакой симуляции на клиенте.
- **Тесты** — ручной раннер: массив `(string Name, Func<bool> Run)` в `TestRunner.cs`, каждый тест
  — статический метод, возвращающий `bool`. Никакого xUnit/NUnit. При добавлении новой механики
  почти всегда нужно добавить 2-5 тестов рядом с похожими.
- **Перед крупными фичами — сначала описать план в чате и получить подтверждение**, только потом
  кодить. Пользователь несколько раз явно просил "сначала скажи, что будешь делать, не кодь".
- После любых серьёзных изменений: `dotnet build` → `dotnet run` тестов → если есть визуальный
  эффект, ещё и живой запуск клиента с скриншотом (см. раздел про верификацию ниже).

## Явные решения по скоупу (не предлагать снова без явной просьбы)

- **Боты для ролей экипажа (инженер/механик/охрана/капитан) осознанно отложены.** Пользователь
  прямо сказал не делать их, пока не попросит явно. Сейчас вся игра — один игрок, который должен
  разрываться между ролями (это принято как есть).
- Реальная сетевая передача (TCP/LiteNetLib вместо in-process) — не начата, `ITransport`
  специально спроектирован так, чтобы это был просто ещё один класс, а не переписывание.

## Текущее состояние: что реализовано

### Phase 1 (MVP) — полностью, и местами глубже плана

- Корабль: 5 комнат в ряд (кокпит/реакторная/коридор/каюты/машинное), двери — проёмы в общей
  стене, AABB-коллизии по осям (`Ship.MoveAlongAxis`).
- **Блочные стены корпуса**: у каждой комнаты периметр собран из блоков 1×1 (`WallBlock`), но
  только по **внешним** стенам корабля (где нет соседней комнаты) — внутренние переборки не
  бьются, там всё равно герметичный сосед, а не вакуум. Игрок при этом ходит свободно, не по
  тайлам — блочность только у стен.
- **Физика кислорода по Barotrauma**: у каждой комнаты `Oxygen` 0-100 (не флаг "пробит/цел").
  Каждая незаваренная пробоина тянет O2 вниз (-3/сек на пробоину). Генератор кислорода
  (физический блок-система "Кислород") качает O2 **только в свою комнату** (коридор), а дальше
  кислород **диффундирует через двери** к соседям пропорционально разнице уровней — дальние
  отсеки наполняются медленнее. Урон персонажу зависит от того, насколько упал O2 (порог 50,
  максимум урона при 0), а не от бинарного флага. Скафандр — полный иммунитет.
- **Множественные независимые пробоины**: враг пробивает случайный целый блок по всему кораблю
  (не "комнату целиком"), в одном отсеке может быть сразу несколько дыр, варится каждая отдельно
  ближайшая (F + держать сварочный аппарат в руке).
- **Инвентарь в стиле Barotrauma**: 9 слотов в ряд + 3 слота экипировки (наушники/одежда/головной
  убор, сейчас реально используется только "одежда" под скафандр). Полоска под слотом — клик
  мышью берёт/отпускает предмет из руки (`Inventory.ToggleHold`).
- **Механика рук**: у персонажа 2 "руки" (ёмкость, не отдельные слоты). Сварочный аппарат/
  автомат/лазерная винтовка — 2 руки, ключ/отвёртка/резак/нож — 1 рука. Взятие предмета,
  которому не хватает рук, автоматически "роняет" ранее взятые (Barotrauma-style).
- **Все предметы из дизайн-дока реализованы** как объекты (можно подобрать, держать в руке):
  AmmoCrate, Spacesuit, Wrench, Screwdriver, WeldingTool, Cutter, Knife, Rifle, LaserRifle,
  FuelRod. У ножа/автомата/лазерной винтовки **нет** геймплейного эффекта (рукопашная/стрельба
  личным оружием — Phase 3, абордаж), это осознанно.
- **Энергосеть, кликабельные блоки**: Реактор (большой блок, 4 слота под ядерные стержни —
  без стержня в хотя бы одном слоте нет выработки тока, даже если топливо есть) + Блок
  распределения (средний, рядом с реактором, слайдеры по 5 системам работают только пока блок
  открыт) + 5 обычных системных блоков (кислород/двигатель/щиты/орудия/прочее — можно
  повредить/починить ключом, у двигателя размер блока увеличен как у реактора). Все блоки —
  "заходишь" кликом левой кнопкой мыши, стоя рядом (радиус как у F-взаимодействия), автозакрытие
  при отходе.
- **Щиты**: общая полоса корабля (100 очков), заряжается только от мощности в слайдере "Щиты".
  Пока заряд > 0 — каждая атака врага поглощается щитом целиком, урон отсекам/турелям/системам не
  проходит вообще.
- Бой: 2 турели (баллистическая в кокпите, лазерная в реакторной — заряжается от слайдера
  "Орудия"), перископ с ограничением угла, боезапас+ящики патронов ИЛИ конденсатор.
- Враг: абстрактный HP, атакует по таймеру, конкурируют турель/система/блок стены, отступает
  <20% HP.
- **Карта галактики со свободной 2D-навигацией (Phase 2, milestone M8)**: заменила старую жёсткую
  цепочку "Transit→Battle→Station по таймеру". 6 фиксированных точек (`GalaxyMap.CreateStarter`),
  корабль стартует пристыкованным к домашней станции. Консоль навигации (кокпит) — кликабельный
  блок, открывает панель карты вместо вида корабля; клик по точке шлёт курс, корабль реально летит
  по прямой (скорость/дистанция имеют значение, не телепорт и не фиксированный таймер). Прибытие
  во враждебный сектор → бой (враг возрождается заново на каждую встречу через `EnemyShip.Reset()`);
  прибытие на станцию → дозаправка/заварка всех пробоин/восстановление кислорода. После победы —
  открытый космос, а не автовозврат на станцию: игрок сам решает, куда лететь дальше. Сменить курс
  посреди боя нельзя (сервер игнорирует).
- **Станционные NPC (Phase 2, milestone M9)**: консоль шлюза (`AirlockConsole`, коридор) —
  кликабельный блок, но открывается **только пока корабль пристыкован** (`Phase == Station`).
  `Station.CreateDefault()` — 2 NPC, одинаковый набор на любой станции пока (дифференциация по
  станциям — не сделана, later): Администратор (задания) и Торговец (снаряжение/ресурсы). Клик по
  NPC показывает статичный текст-заглушку диалога ("заданий пока нет" / "склад пуст") — реальных
  транзакций и заданий ещё нет, это база для M10 (экономика) и M11 (доставка груза). Полноценной
  ходьбы по станции (отдельная сцена/тайлмап станции) нет и не планировалась для этого milestone —
  сознательное упрощение против буквального текста дизайн-дока.
- **Экономика (Phase 2, milestone M10)**: один общий кошелёк экипажа (`World.Credits`, старт 300),
  не по-игрочно — со-оп рамка, деньги общие на корабль. Фиксированный каталог Торговца
  (`TradeCatalog`, 7 позиций из уже реализованного Phase 1 снаряжения — ключ/отвёртка/сварочный
  аппарат/резак/скафандр/ящик патронов/ядерный стержень) с ценой покупки и отдельной, всегда более
  низкой ценой продажи; нож/автомат/лазерная винтовка сознательно не в каталоге — у них пока нет
  геймплейного эффекта (см. решение по Phase 3 абордажу). Покупка/продажа — только пока пристыкован
  (`VoyagePhase.Station`), та же проверка, что у консоли шлюза. Клиент: панель Торговца показывает
  две колонки (купить/продать) поверх текста-заглушки для Администратора, который остаётся
  заглушкой (задания — M11). Ни разной цены по станциям, ни скидок от репутации — сознательно не
  делали, это позже.
- **Задания на доставку груза (Phase 2, milestone M11)**: только тип "доставка", без добычи
  минералов/убийств/спасения груза/пассажиров (те — Phase 3, см. дизайн-док §7). Одно активное
  задание одновременно на весь экипаж (`World.ActiveCargoQuest`, упрощение лимита станции до 1 для
  соло-MVP), груз — абстрактный статус "задание принято", **без** физического предмета-ящика и без
  отдельной стойки хранения под него (design doc §7 описывает три типа хранения, но пока нечему
  угрожать целостности груза — ни порчи от разгерметизации, ни кражи, — физический предмет
  сознательно отложен до появления реального failure mode). У Администратора — один и тот же клик
  по кнопке в диалоге меняет смысл по состоянию: нет задания → "взять" (сервер сам выбирает
  случайную станцию `!= текущей` из `GalaxyMap`, фиксированная награда 100 кредитов); задание есть,
  но не на этой станции → просто статус без кнопки; задание есть и корабль как раз здесь →
  "сдать груз". Оба действия (`AcceptCargoQuestPressed`/`TurnInCargoQuestPressed`) — только пока
  пристыкован, та же проверка что у Торговца и консоли шлюза.
- **Медик + упрощённые травмы (Phase 2, milestone M12)**: аптечка (`ItemType.MedKit`, 1 рука, точка
  выдачи в каютах `medkit-quarters`, есть и в каталоге Торговца — 50/20). Кровотечение —
  `Character.IsBleeding` (вычисляемое свойство: `Health > 0 && Health < 50`), не отдельный флаг —
  чисто по текущему здоровью. Пока кровоточит, каждый тик идёт **дополнительный** пассивный урон
  (`World.Injuries.cs`, -2/сек) поверх любой другой причины (сейчас единственная другая причина —
  декомпрессия) и **не останавливается**, когда персонаж уходит из опасного отсека — травма
  сохраняется, пока её не вылечат. Лечение — аптечка в руке + F в любом месте (не станция, не нужна
  привязка к объекту): восстанавливает 50 HP разово и расходуется; на полном здоровье F с аптечкой
  ничего не делает (не тратится зря). **Осознанно не делали**: именованные типы травм (кровотечение/
  ожоги/удушье как отдельные состояния — тут одно обобщённое "кровотечение" на любую причину),
  лечение других персонажей (только себя — таргетинг для соло-MVP не нужен), смерть/возрождение на
  станции (`Character.Health` может дойти до 0 без последствий — это отдельная, более крупная фича,
  не входившая явно в согласованный скоуп M12).
- **Прокачка корабля (Phase 2, milestone M13)**: третий NPC на станции — Механик
  (`NpcKind.Mechanic`, всегда рядом с Администратором/Торговцем, та же станционная упрощённость).
  3 дискретных уровня (`ShipUpgradeCatalog`, цены 200/400/800 за уровень, единые для всех станций)
  по 3 направлениям: выработка реактора (+15 к `Reactor.MaxOutput` за уровень — `MaxOutput` теперь
  вычисляемое свойство "база + бонус", а не readonly-поле, так что все места, которые его читают —
  HUD, `PowerGrid`-клампы — подхватывают апгрейд без доп. правок), экономичность реактора (×0.8
  расхода топлива за уровень, мультипликативно), урон орудий (+3 к `DamagePerShot` за выстрел,
  общий бонус на оба орудия, не отдельно на каждое). Апгрейды — общие на экипаж, как кредиты,
  сохраняются насовсем (пути отката/потери уровня нет). Только пока пристыкован — та же проверка,
  что у Торговца/Администратора. **Осознанно не делали** (см. `ShipUpgradeTrack.cs`): прочность
  корпуса/систем — нет числового HP-пула ни у корпуса, ни у систем, только бинарное
  пробито/повреждено, апгрейдить нечего; мощность двигателя — слайдер "Двигатель" пока вообще ни на
  что не влияет (скорость полёта по карте — фиксированная константа, не связана с распределением
  энергии), апгрейдить бы пришлось эффект-пустышку; ёмкость аккумуляторов — аварийное
  переключение на батарею при поломке реактора (design doc §1) тоже не реализовано (`Battery.cs`
  прямо это фиксирует), больше ёмкости для того, что никто не тратит — чисто косметика.
- **Кастомная прокладка проводов (Phase 2, milestone M14, последний пункт Phase 2)**: полная
  версия по дизайн-доку — реактор → distribution → магистраль (`trunk-*`) к каждой из 5 систем →
  локальная коробка (`Junction`-узел) → отвод (`drop-*`) к конкретному физическому устройству
  (`WireNetwork.cs`). **Щиты — единственная система с двумя физическими генераторами** (кокпит +
  каюты, `system-shields`/`system-shields-2`), ровно как в примере из дизайн-дока — это то, что
  реально даёт "два уровня отказа" смысл: перебить магистраль (`trunk-shields`) роняет систему
  целиком, перебить один-единственный отвод (`drop-shields-2`) режет эффективную мощность щитов
  ровно пополам, а не до нуля (`World.GetEffectivePower`). У остальных 4 систем всего одно
  устройство, так что для них разница между "магистраль перебита" и "отвод перебит" не наблюдаема
  снаружи (оба дают 0) — это не баг, а следствие того, что в игре пока нет других систем с
  несколькими физическими блоками.
  **Сознательное упрощение интерфейса** (обсуждено и согласовано с пользователем явно, до начала
  кодинга): вместо буквального "кликнуть по двум произвольным точкам схемы, чтобы соединить их
  проводом" — один клик по уже существующей линии провода в новой панели (щёлкнуть блок
  "Проводка" рядом с distribution-блоком, `WiringTerminal`), а то, что в руке, решает, что
  происходит: ключ/отвёртка чинят повреждённую половину (магистраль или резерв), катушка провода
  (`ItemType.WireSpool`, новый предмет, есть в каталоге Торговца и на стойке в машинном отделении)
  кладёт резервный провод на выбранную линию, если резерва там ещё нет — один резерв на линию,
  не бесконечно. Резерв **не убирает** уязвимость, а даёт запас прочности: враг может перебить и
  сам резерв отдельным попаданием (`World.EnemyAi.cs` теперь целится в конкретный провод — основной
  или резервный, смотря что сейчас реально несёт питание — а не в "систему" целиком одним флагом).
  Ремонт через панель **не требует физического присутствия** у конкретного устройства (в отличие
  от старого ремонта ключом прямо на блоке системы, который тоже остался и работает — чинит то же
  самое, местно, если стоять рядом с конкретным повреждённым устройством).
  **Крупный сопутствующий рефакторинг**: `PowerGrid` лишился концепции повреждения целиком
  (`SetDamaged`/`IsDamaged` убраны) — теперь это чистый калькулятор слайдер-аллокации, а "реально
  ли питание доходит до системы" полностью переехало в `World.Wiring.cs`
  (`World.GetEffectivePower`/`IsDeviceConnected`, оба публичные). `ShipSystemState` стал
  per-device (`DeviceId` добавлен), а не per-system — иначе два генератора щита не смогли бы иметь
  независимое визуальное состояние "повреждён/цел". Все существующие точки чтения старого API
  (диффузия кислорода, подзарядка лазера, зарядка щита, ремонт по клику, ИИ-повреждения, HUD)
  переведены на новый.

### Phase 3 (milestones M15-M18) — открытый космос, шлюз/вакуум, выход в космос, добыча

Реализовано за одну сессию по явному запросу пользователя ("ВПЕРЕД! реализуй этот план") после
обсуждения в чате и явного выбора скоупа через AskUserQuestion. Все 4 milestone'а сделаны и
протестированы; ниже — по одному разделу на каждый.

**M15 — физическое движение корабля, инерция, штурвал, столкновения.**
Новая точка на карте галактики (`GalaxyPointKind.AsteroidField`, "Пояс астероидов Эпсилон") и
новая фаза `VoyagePhase.AsteroidField`: вместо автополёта по прямой (как в `Traveling`) корабль
здесь — физическое тело с позицией/углом/скоростью/вектором тяги (`World.ShipField.cs`), которое
пилотируют вручную. Штурвал (`HelmConsole`, кокпит) — заходишь через F (как турель), на клиенте
появляется джойстик-панель в стиле Baротравмы (`HelmPanel`): тянешь ручку мышью от центра —
направление и дальность от центра задают вектор тяги; **вектор тяги персистентный** — отпустил
мышь или встал из-за штурвала, последняя заданная тяга продолжает применяться каждый тик, пока её
явно не поменяют (кнопка "Стабилизация" гасит тягу и скорость до нуля). Разгон/торможение
масштабируются реальной эффективной мощностью на `Engine` (`GetEffectivePower`) — без энергии
корабль либо не разгоняется, либо (при стабилизации) не может затормозить, это осознанно совпадает
с "двигается, только если подана энергия" из обсуждения. Астероиды (`Asteroid`, `AsteroidField`,
5 штук, поле 300×300 юнитов — специально большое, чтобы корпус корабля ~26×6 и манёвры внутри поля
не упирались в границы) — неразрушимые круги; столкновение проверяется через oriented-box-vs-circle
(корпус корабля как повёрнутый прямоугольник по объединённым габаритам всех комнат,
`GetHullLocalBounds`) — при контакте скорость гасится в ноль и **пробивается ближайший к точке
касания `WallBlock`** обшивки (переиспользован тот же механизм пробоин, что и у ИИ/декомпрессии, не
новая система). **Осознанное упрощение**: столкновение просто гасит скорость целиком (не скользит
вдоль поверхности) — этого достаточно для геймплейного смысла "врезался — получил пробоину, дальше
торможение вручную".

**M16 — двери с состоянием, шлюзовая камера, вакуум.**
Общий механизм для **всех** дверей корабля (не только шлюза): у `Door` появилось состояние
открыта/закрыта (`DoorState`), переключается кликом ЛКМ прямо на виде корабля (без проверки
близости на сервере — тот же уровень доверия клиенту, что у `WireLinkInteractId`/слайдеров питания),
закрытая дверь блокирует и движение персонажа (`Ship.MoveAlongAxis` теперь принимает
`Func<string,bool> isDoorOpen`), и диффузию кислорода через неё (`World.Atmosphere.cs`). К ряду
комнат добавлена шлюзовая камера (`airlock-chamber`, за машинным отделением) с обычной дверью внутрь
корабля и **новым типом** — `AirlockOuterDoor` (`door-airlock-vacuum`), которая ведёт не в комнату, а
в открытый космос: он **не отсек**, кислород там всегда 0 напрямую, не через `_roomOxygen`. Открытая
внешняя дверь тянет кислород камеры к нулю по той же формуле диффузии, что и обычная дверь (только
"вторая комната" всегда пустая) — открыть её, не закрыв внутреннюю дверь, реально разгерметизирует
весь корабль по цепочке; закрыть внутреннюю дверь — жертвуешь только камерой. Никакой блокировки
"нельзя открыть обе двери шлюза одновременно" **нет и не планировалась** — это симуляционная игра,
последствия должны быть реальными, а не гарантированными системой. Отдельно от существующей
`AirlockConsole` ("Шлюз" — кнопка стыковки с NPC станции, не физическая дверь) — разные фичи с
похожим названием, не перепутать.

**M17 — выход в открытый космос (EVA), магнитные ботинки, ранец.**
Из шлюзовой камеры, в скафандре, через **открытую** внешнюю дверь и **только пока корабль в фазе
`AsteroidField`** (иначе снаружи буквально нет физического пространства, чтобы там оказаться) —
персонаж пересекает в ту же самую систему координат, что и корабль снаружи, не отдельную сцену
(`World.Eva.cs`). По умолчанию — "примагничен" (`EvaAttachment.Ship`/`.Asteroid`): двигается в
локальных координатах того объекта, к которому прицеплен (для корабля — с учётом его текущего
поворота, `RotateWorldToLocal`/`RotateLocalToWorld`; для астероида поворота нет, они не вращаются).
Пробел с прицелом по курсору мыши — оттолкнуться, стать свободно летящим телом со своей скоростью;
WASD в свободном полёте — тяга ранца (`JetpackFuel`, максимум 100, расход 10/сек, ускорение
1 юнит/с²) — кончилось топливо, вектор тяги перестаёт применяться, но инерция остаётся навсегда
(бесконечный дрейф, как и обсуждали). Автоматическое примагничивание срабатывает само при
приближении к кораблю/астероиду (никакой отдельной кнопки "прицепиться" не нужно). **Изначально не
было сделано** (позже устранено отдельной внеплановой сессией "единая камера корабль/космос", см.
раздел ниже): интерьер и открытый космос рисовались двумя независимыми переключаемыми по флагу
рендерерами с разным масштабом, силуэт корабля снаружи был плоским повёрнутым прямоугольником, а
видимость снаружи не была ничем ограничена (в отличие от конуса фонаря внутри).
**Важная деталь реализации** — переход через дверь (в обе стороны) обязательно "отодвигает"
персонажа на небольшую дистанцию **дальше** порога (`EvaExitNudge`/`EvaEntryNudge`), а не ровно на
границу — иначе следующий же тик того же движения снова попадает в прямоугольник двери и линия
перехода мгновенно срабатывает в обратную сторону (поймано и исправлено дважды — один раз на выходе,
один раз на входе, оба раза выглядело как "персонаж не может пройти дальше двери").

**M18 — добыча астероидов.**
1-3 жилы руды на поверхность каждого астероида (`OreDeposit`, конечное число ударов
`MaxHits` — 2 или 3). С резаком в руке, рядом с жилой (та же клавиша F, что и везде — не отдельная
клавиша под добычу) — один удар снимает `RemainingHits` на 1 и **выбрасывает предмет руды рядом**
(`DroppedItem`, новая сущность — впервые в игре предмет лежит в мире сам по себе, не в инвентаре и
не на фиксированной станции), а не сразу в инвентарь; подобрать — тем же F, отдельным нажатием
(F сначала проверяет, нет ли рядом уже лежащей руды — если есть, поднимает её, а не бьёт жилу ещё
раз). Выработанная жила (`RemainingHits == 0`) перестаёт реагировать на F насовсем. **Сознательное
упрощение экономики** (не обсуждалось отдельно, решено при реализации ради объёма): руда — это
**обычный товар в каталоге Торговца** (`ItemType.Mineral`, цена продажи 35, цена покупки специально
неэкономичная 999, чтобы не покупали обратно) и продаётся через уже существующий дженерик-механизм
продажи (`TrySellItem`), а **не** отдельное "задание на добычу" с явным принятием/сдачей как у
доставки груза (M11) — из инвентаря она пропадает и превращается в кредиты ровно так, как просил
пользователь ("при завершении задания минералы из инвентаря пропадают"), просто без обёртки-квеста
поверх. Если нужен именно квест-флоу (принять задание у Администратора → добыть N руды → сдать) —
это отдельная, не начатая доработка.

### Внеплановая сессия — визуальный апгрейд, анимации инструментов, выбор корабля

Не milestone из дизайн-дока, а прямой запрос пользователя ("перерисуй все текстуры в стиле
Space Station 13/Barotrauma, добавь анимации варки/резки, создай несколько кораблей на выбор"),
реализовано за одну сессию сразу после M15-M18. Три независимых куска работы:

**Визуальный стиль (клиент, без изменений протокола).** В проекте нет реального пайплайна
спрайтов/изображений (`Content Pipeline` используется только для `SpriteFont`) — весь рендер и
раньше, и сейчас идёт через один `1x1`-пиксель (`_pixel`), закрашенный/повёрнутый/отмасштабированный
через `SpriteBatch`. Скачивать реальные ассеты SS13/Barotrauma было бы нарушением авторских прав, так
что вместо "перерисовки текстур" сделан **процедурный индустриальный стиль**, полностью на том же
`_pixel`: `ShipRenderer.DrawPanel`/`DrawRivets`/`DrawHazardStripes`/`DrawFloorGrating` — общий язык
для всех кликабельных блоков (фаска+заклёпки по углам, шевроны "опасность" на дверях/повреждённых
системах/пробоинах), персонаж вместо плоского квадрата — "шлем"+корпус+насечка направления взгляда
(`FacingX/Y`, уже было в протоколе, просто не использовалось визуально). В `FieldRenderer` —
астероиды теперь рваный силуэт (несколько повёрнутых квадратов-"долек" + кратеры, форма
детерминирована по `Asteroid.Id` через seed, не мигает между кадрами), руда/подобранные предметы —
пульсирующий "кристалл" (повёрнутый на 45° квадрат). Свечение двигателя у кормы, масштабируемое
текущей тягой (`ShipFieldState.ThrustX/Y`), сохранилось и после того, как отдельный силуэт корпуса
снаружи был убран (см. раздел "единая камера корабль/космос" ниже) — теперь рисуется прямо поверх
настоящих комнат, которые и играют роль видимого корпуса.

**Анимации сварки/резки/ремонта.** Обе механики (заварить пробоину, срезать руду резаком, починить
систему ключом/отвёрткой) уже существовали как мгновенные серверные действия по F — новых
геймплейных механик тут нет, добавлена только визуальная реакция. Реализовано **чисто на клиенте**,
без изменений протокола: `EffectTracker` (`Client/Rendering`) сравнивает два последовательных
`WorldSnapshot` и по разнице состояний (`WallBlockState.Breached` true→false, `OreDepositState.
RemainingHits` уменьшилось, `ShipSystemState.Damaged` true→false) сам порождает короткоживущий
`TransientEffect` — вспышку искр (`DrawSparkBurst` в обоих рендерерах) в точке события. Сервер ничего
не знает об этих эффектах и не обязан ничего специально слать — при необходимости то же самое
сработает и по сети, без доп. полей в снапшоте.

**Три класса корабля на выбор (`game_design.md` §9).** `Ship` стал `partial` с диспетчером
`Ship.Create(ShipKind)`: `ShipKind.Frigate` — старый M2-стартовый корабль без изменений (5 комнат,
2 орудия, дефолт), `ShipKind.Scout` (`Ship.Scout.cs`) — 2 комнаты, 1 (более слабое) орудие, **нет**
станций автомата/лазерной винтовки (только нож) — специально слабее и меньше, не только меньше,
`ShipKind.Cruiser` (`Ship.Cruiser.cs`) — 7 комнат (добавлен трюм "hold"), 3 орудия, второй склад
патронов. Все три класса используют **одинаковые 6 id физических устройств питания**
(`system-shields`/`system-shields-2`/`system-weapon-charger`/`system-oxygen`/`system-secondary`/
`system-engine`) — это не эстетика, а необходимость: `WireNetwork.CreateDefault()` — фиксированная
топология, которая ссылается на эти id напрямую как на id узлов схемы (см. её собственный
doc-comment), и с другими id устройство просто тихо стало бы "всегда под током" вместо реального
участия в мини-игре починки проводки (`World.Wiring.cs.IsDeviceConnected` деградирует молча, не
падает — но чинить в нём было бы нечего). Выбор корабля — экран **перед стартом сессии** в `Game1`
(клавиши 1/2/3, `ShipCatalog` даёt название/описание): `SoloSession`/`GameServer`/`World` все получили
необязательный параметр `ShipKind = ShipKind.Frigate`, так что все ~100 старых вызовов `new World()`
в тестах остались нетронутыми и ведут себя как раньше.

**Осознанно не делали** (сознательное сужение скоупа, не обсуждалось отдельно — если нужно другое,
поправить): экономика/цены/привязка к репутации для выбора корабля (design doc §9 — "все классы
доступны с самого начала, но дороже/дешевле") — сейчас все три класса просто свободно выбираются в
начале новой игры, никакой покупки/продажи корабля в игре ещё нет, это отдельная будущая доработка;
разная физика полёта на разных классах (масса/манёвренность) — у всех кораблей одинаковые константы
инерции/тяги (`World.ShipField.cs`), разница только в планировке/вооружении; переключение корабля
посреди уже идущей игры — выбор ровно один раз, при старте новой сессии.

проверялся, в этой песочнице нет инструмента для управления нативным MonoGame-окном (см. пункт 4);
вся логика проверена тестами, гоняющими тот же серверный код, что вызывает клиент.

## Известные грабли / уроки этой сессии

1. **Диагональное движение персонажа в тестах может промахнуться мимо двери.** Дверь — узкий
   проём (высота ~1.8 юнита) в общей стене; если двигаться по диагонали к цели с другим Y, чем
   спавн, есть шанс, что Y выйдет за пределы проёма как раз в момент пересечения X. В хелперах
   тестов (`MoveCharacterTo`) для перехода в другую комнату сначала идти горизонтально на той же
   высоте, что и текущая позиция (обычно Y=3, высота дверей), и только потом двигаться по
   вертикали внутри уже нужной комнаты.
2. **`ApplyCommand` не мёржит поля между вызовами.** Каждый `ClientCommand` перезаписывает
   `PowerSystemIndex`/`PowerDirection`/`MoveX`/`MoveY` и т.д. своими значениями (по умолчанию
   "ничего"). Если нужно одновременно двигать слайдер энергии И, например, лететь по карте —
   это **один** `ClientCommand` с обоими полями, а не два последовательных вызова (второй вызов
   без явного `PowerDirection` сбросит слайдер на 0 раньше, чем он успеет подействовать).
3. **Шрифт `DebugFont` не покрывает всю Unicode-пунктуацию.** `CharacterRegions` в
   `Content/DebugFont.spritefont` — это ASCII (0x20-0x7E) + кириллица (0x0400-0x04FF) + после
   этой сессии ещё общая пунктуация (0x2010-0x2027: тире, кавычки, многоточие). **Любой символ вне
   этих диапазонов в строке, которая реально уходит в `SpriteBatch.DrawString`, роняет всё
   приложение необработанным исключением** (`ArgumentException` в `SpriteFont.GetGlyphIndexOrDefault`)
   — это не "текст выглядит криво", это краш. Проверять новые строки интерфейса на такие символы;
   расширять `CharacterRegions` при необходимости (это XML, пересобирается автоматически через
   MonoGame Content Pipeline при `dotnet build`).
4. **Живая проверка через синтетические клики/клавиши в этой песочнице ненадёжна.** Между
   скриншотами окно игры может физически сместиться на экране (из-за самого чат-интерфейса), и
   заранее вычисленные координаты клика промахиваются — в т.ч. могут случайно попасть в чат и
   вписать туда мусорный текст (проверять и очищать поле ввода, **не отправляя** его, если это

   есть заметный визуальный/интерактивный эффект.
7. **Долгий wait-луп перед измерением в тесте может сам "сжечь" измеряемую величину.** Было
   ~20% нестабильности в `World_Decompression_DrainsHealthInBreachedRoom` и
   `World_SuitedCharacter_ImmuneToDecompression`: измеряемый персонаж всё это время (поиск нужного
   состояния мира + "отстой" до нужного уровня кислорода, суммарно до 900 симулированных секунд)
   уже стоял в опасной комнате, и здоровье успевало упасть до 0 задолго до самого окна измерения
   before/after — тогда `after < before` ложно проваливалось, потому что оба замера читали уже
   "дно". Дело было не в недостаточных таймаутах (это чинили дважды до того, и всё равно ~20%
   флейка оставалось) — причина в том, что персонаж вообще не должен быть в опасности во время
   долгого поиска. **Фикс**: заводить/перемещать измеряемого персонажа в опасную комнату
   непосредственно **перед** самим окном измерения (1 секунда), а не держать его там всё время
   поиска нужного состояния мира. Проверено 8 подряд чистыми прогонами всего набора тестов.
8. **Тест, ждущий "чистый" случайный исход через retry-цикл, должен считать реальную вероятность
   попытки, а не гадать сколько попыток "обычно достаточно".** При добавлении
   `World_Oxygen_GeneratorRestoresRoomOxygenWhenPowered` тест ждал через `new World()` + один цикл
   боевой атаки ИИ ровно один изолированный исход — пробоина именно в коридоре и нигде больше на
   корабле (иначе диффузия в разряженные соседние комнаты забивает эффект питания). С бюджетом в
   50 попыток тест падал ~1 раз из 15-20 — не из-за бага в игре и не из-за коллизий seed у
   `new Random()` (проверено отдельно: коллизии первого броска на 200k случайных экземпляров ~
   5/200000, не источник флейка), а потому что вероятность попадания в нужный исход с одной попытки
   — **всего ~7%** (пробоина по стенам это ~42% исходов атаки ИИ, и лишь ~1/6 всех блоков корпуса
   корабля — стены именно коридора). При такой вероятности 50 попыток дают ~2-3% шанс ни разу не
   попасть — то есть ровно наблюдаемый флейк. **Фикс**: не увеличивать таймауты/подождать дольше, а
   явно посчитать вероятность одной попытки и подобрать бюджет попыток так, чтобы шанс полного
   провала был пренебрежимо мал (подняли до 300 попыток, каждая попытка дешёвая — доли
   миллисекунды симуляции). Разово оставлял `Console.WriteLine` внутри теста при отладке, чтобы
   различить "не нашли изолированный сценарий за N попыток" от "нашли, но кислород всё равно
   просел" — это и разделило гипотезы. Проверено 25 подряд чистыми прогонами.
9. **Изолированная одна пробоина в комнате почти не опасна, если соседние комнаты целы —
   диффузия от полных соседей перекрывает утечку.** При добавлении теста на кровотечение
   (`World_Bleeding_...`, M12) попытка "получить урон, потом дойти до шлюзового шкафчика в
   машинном и надеть скафандр, чтобы изолировать кровотечение от декомпрессии" **стабильно** (30/30
   попыток) проваливалась с здоровьем ровно 0 после надевания скафандра — не флейк, а системная
   причина: чтобы коридор реально просел по кислороду, нужно **масштабное** повреждение по всему
   кораблю (long random combat), а значит к моменту, когда персонажа можно ощутимо ранить, машинное
   отделение на другом конце корабля тоже почти наверняка уже пробито — идти туда не безопаснее, чем
   оставаться на месте. Матиматически: при одной пробоине в коридоре и обоих соседях на 100 —
   равновесие устанавливается на ~97 (приток от соседей 0.5×(100-x)×2 почти полностью перекрывает
   утечку 3/сек) — то есть по конструкции игры **изолированная** пробоина не может быть по-настоящему
   опасной, опасность обязательно системная (много пробоин сразу). **Фикс**: не пытаться физически
   переместить/заизолировать персонажа скафандром — вместо этого завести **двух** персонажей в одну
   и ту же комнату в разные моменты (один "зашёл" раньше и уже кровоточит, второй свежий, ещё выше
   порога), сравнить скорость падения здоровья у них в один и тот же тик при одинаковом кислороде —
   разница целиком приписывается кровотечению, без необходимости куда-то идти или во что-то
   переодеваться. Диагностировано через временный `Console.WriteLine` внутри теста (показавший
   `health=0` после надевания скафандра во всех 30 попытках подряд — не похоже на удачу). Проверено
   30 подряд чистыми прогонами после фикса.
10. **`timeout N dotnet run --project ...` в этой песочнице не всегда убивает дочерний .exe.**
    После `dotnet run --project src/SpaceAdventure.Client --no-build`, убитого через `timeout`,
    `SpaceAdventure.Client.exe` иногда продолжает висеть в фоне и блокирует DLL при следующей
    `dotnet build` (ошибка копирования файла, "занят другим процессом"). Проверять
    `Get-Process -Name SpaceAdventure.Client` после такой проверки и явно `Stop-Process -Force`,
    если процесс остался — не полагаться на то, что `timeout` сам всё почистил.
11. **`MoveCharacterTo`-хелпер ломается, если целевая Y отличается от высоты дверей (обычно 3), а
    путь пересекает несколько комнат.** Диагональный bang-bang контроллер идёт к цели равными
    шагами по X и Y одновременно — если |ΔY| меньше |ΔX|, Y "заканчивается" раньше, чем персонаж
    успевает пройти все двери по X, и застревает у ближайшего порога (Y уже вне диапазона проёма).
    Это НЕ новый баг M15-M18, тот же паттерн, что и пункт 1 выше, но он укусил заново несколько раз
    за эту сессию (в т.ч. молча — тест "проходил" только потому что персонаж случайно не заходил
    туда, куда думали) просто потому что новые milestone'ы требовали ходить в более отдалённые
    комнаты. **Практическое правило**: если хоть один из компонентов пути лежит в другой комнате —
    сначала `MoveCharacterTo(x, 3f)` до нужного X на высоте дверей, потом отдельным вызовом
    `MoveCharacterTo(x, targetY)` внутри уже нужной комнаты. Не полагаться на один прямой вызов.
12. **`_moveInput` не сбрасывается сам — тестовый хелпер обязан явно прислать `MoveX:0,MoveY:0`,
    когда заканчивает временное движение.** В реальном клиенте это не проблема (свежий ввод с
    клавиатуры шлётся каждый кадр, по умолчанию (0,0)), но в тестах, где `ApplyCommand` вызывается
    вручную, "забытое" ненулевое значение продолжает действовать бесконечно после того, как тест
    перестал его слать. Для движения внутри корабля это почти всегда безобидно (комната ограничивает
    результат), но для EVA (`World.Eva.cs`) — нет: прикреплённый к кораблю персонаж с "забытым"
    вводом продолжает идти по корпусу сам по себе тик за тиком, что один раз привело к тому, что тест
    решил, будто персонаж прошёл через шлюз обратно внутрь, хотя это сделал остаточный ввод из
    предыдущего шага теста, а не то, что тест намеренно проверял. **Фикс**: `WalkFixedDirection`
    (новый тестовый хелпер для подхода к внешней двери шлюза) сам шлёт финальный `MoveX:0,MoveY:0`
    перед возвратом; в остальных местах, где ввод шлётся вручную в цикле, — присылать явный
    стоп-кадр перед следующим этапом теста, если дальше идёт `Step()` без своих команд.
13. **Односторонний переход через границу (дверь-в-вакуум, возврат из вакуума) должен "отодвигать"
    персонажа дальше порога, а не ставить ровно на него.** Прямоугольник двери имеет реальную
    ширину (~1 юнит) — если после перехода персонаж оказывается ровно на границе или где-то внутри
    этого прямоугольника, то **тот же самый** тест "нахожусь ли я в проёме" на следующем тике снова
    даёт true, и переход мгновенно срабатывает в обратную сторону — персонаж как будто "не может"
    пройти дальше двери, зависает точно на пороге. Это разные баги на выходе и на входе (нашлись и
    чинились отдельно, `EvaExitNudge`/`EvaEntryNudge` в `World.Eva.cs`), но одна и та же причина:
    решение перейти границу обязано сразу отодвинуть позицию за пределы прямоугольника перехода
    (расстояние нуджа больше ширины самого прямоугольника), а не просто зафиксировать "точку
    контакта".
14. **Отталкивание от корабля (push-off) сразу после выхода начинается буквально внутри зоны
    авто-прицепления** — зона (`ShipAttachZoneMargin`) специально шире, чем нужно для реалистичного
    "притягивания" при возврате, а точка выхода из шлюза (`EvaExitNudge`) намеренно небольшая, чтобы
    не телепортировать персонажа далеко. Из-за этого без специальной защиты отталкивание немедленно
    "прилипало" обратно на первом же тике свободного полёта, ничего не давая игроку. **Фикс**:
    `PushOffGraceRemaining` — короткое окно (3 секунды) сразу после отталкивания, в течение которого
    проверка авто-прицепления полностью выключена, вне зависимости от фактической позиции — даёт
    физике время реально унести персонажа за пределы зоны, прежде чем прицепление снова начнёт
    проверяться. Слишком короткое окно (пробовали 1с, затем 1.5с) не гарантирует выход из зоны при
    более пологом угле отталкивания — 3с даёт запас для любого разумного направления.
15. **`Game1.UnloadContent()` разыменовывало `_session` безусловно, хотя оно остаётся `null`
    (за фасадом `= null!`) до тех пор, пока игрок не выберет корабль на стартовом экране.**
    Обнаружено на практике во время единой-камеры-сессии: фоновый запуск клиента для проверки
    сборки закрылся до нажатия 1/2/3 — `UnloadContent` тут же уронил `NullReferenceException`
    (падение процесса ещё и оставило `SpaceAdventure.Client.exe` висеть и блокировать DLL для
    следующей сборки, см. пункт 10 выше). **Фикс**: `_session?.Dispose()` вместо
    `_session.Dispose()`. Не связано с M15-M18/единой камерой по сути, просто впервые
    проявилось при их проверке.

### Сессия — оставшийся Phase 3 целиком (абордаж, фракции, экономика кораблей, типы станций, типы заданий)

Прямой запрос пользователя "выполняй без остановок всё что можешь по плану, пока не закончишь
этап". Закрыты **все** оставшиеся пункты Phase 3 из `game_design.md` §12, кроме сознательно
отложенного найма ботов у кадровика.

**Абордаж** (`World.Boarding.cs`, `EnemyShipLayout.cs`, `WeaponDefinitions.cs`,
`Client/Rendering/BoardingRenderer.cs`). Личное оружие (нож/автомат/лазерная винтовка) с M3 лежало
в игре предметами **без единого геймплейного эффекта** — теперь это оружие абордажа. Вражеский
корабль стал третьей ходибельной структурой по тому же шаблону, что станция: свои `Rooms`/`Doors`,
общая коллизия через `RoomLayout`, флаг `Character.OnEnemyShip` (рядом с `OnStation`), переход из
`StepCharacters`. Бой начинается в реальном field-space (`Arrive` теперь ставит `_shipFieldPosition`
и для `Battle`, не только для астероидного поля), EVA разрешён в фазе `Battle`, вражеский корпус
виден в космосе — долететь в скафандре, влететь в пробоину, зачистить 3 отсека. Защитники стоят по
одному на отсек и отстреливаются по тому же интервальному таймеру, что и корабельный ИИ
(`World.EnemyAi.cs`). Оружие бьёт только **в своём отсеке** и в пределах дальности — нож 1 юнит
(милишный), автомат 6, лазерная винтовка 8; стены реально держат выстрел, иначе зачистка «отсек за
отсеком» не имела бы смысла. Зачистка всего экипажа = захват корабля, альтернативное условие победы
вместо расстрела из турелей. Апгрейд «урон оружия» у Механика применяется и здесь (он про оружие
вообще, а не про турели).

**Фракции и репутация** (`FactionId.cs`, `FactionDefinitions.cs`, `World.Factions.cs`). Три силы:
Независимые (нейтральны навсегда, владеют домашней станцией), Консорциум, Вольный флот. Репутация
−100..+100 на общий счёт экипажа (как кредиты), двигается ровно от двух событий: сдача задания
фракции (+12) и уничтожение её корабля (−18 ей, +6 её сопернику — асимметрия и есть цена выбора
стороны). Влияет на **цены** (союзникам ×0.8, врагам ×1.35, независимым всегда ×1.0 — множитель
инвертируется на продаже) и на **выдачу заданий** (при ≤ −40 администратор фракции перестаёт давать
работу). Точки галактики получили `Faction`.

**Экономика кораблей** (`World.ShipPurchase.cs`, `ShipCatalog` + цены, `NpcKind.Shipwright`).
Три класса теперь покупаются в игре у Корабельного мастера: Разведчик 400 / Фрегат 900 / Крейсер
1800, при обмене возвращается 60% стоимости текущего корпуса — смена класса всегда чего-то стоит,
а размен вниз выплачивает разницу (отрицательная цена — сознательно разрешённый случай). `World.Ship`
стал `private set`: смена корпуса пересобирает турели/кислород/двери/пробоины через общий
`InitializeShipState()` (тот же метод, что и в конструкторе — чтобы пути не разошлись) и
переставляет экипаж на новую точку спавна. Инвентарь, кредиты и купленные апгрейды переживают
смену — они принадлежат экипажу, а не корпусу.

**Типы станций** (`StationKind.cs`, переписанный `Station.Default.cs`). §10 «у разных станций
разный набор модулей/услуг» — набор услуг это буквально набор NPC: `Outpost` (администратор +
торговец, домашняя), `Trade` (+ механик), `Shipyard` (торговец, механик, корабельный мастер — и
**только** здесь продаются корпуса). Планировки генерируются из списка услуг общим билдером, id
комнат/дверей префиксуются типом (состояние дверей — один плоский словарь на все структуры игры).
`World.Station` стал вычисляемым по текущей/целевой точке, а не одним фиксированным экземпляром.

**Типы заданий** (`Quest.cs` вместо `CargoQuest`, переписанный `World.Quests.cs`). Три вида:
доставка (сдать в точке назначения), охота за головой (уничтожить корабль в секторе — засчитывается
в момент убийства, но награда забирается лично у выдавшего), добыча (принести 2 руды — реально
изымается из инвентаря, не абстрактный флаг). Администратор показывает **доску заданий** — игрок
выбирает вид, а не получает случайный (`ClientCommand.AcceptQuestKind`); это заодно сделало старые
тесты доставки детерминированными.

**Тесты**: 131/131 (было 126 на начало сессии, +19 за неё суммарно: 5 на абордаж, 5 на фракции,
4 на верфь, 5 на новые квесты). 5 прогонов подряд чистые.

### Сессия — сохранения, преступность на станции, эскадры

Пользователь попросил идти дальше без остановок. Из оставшегося взят порядок «сначала то, без чего
всё остальное обесценивается»: сохранения → воровство/арест → групповые бои.

**Сохранения** (`SaveGame.cs`, `World.Save.cs`, `SaveStore.cs`). До этого **сейвов не было вообще**,
хотя `game_design.md` §5 требует автосохранение при каждой стыковке — вся построенная экономика
жила до закрытия окна. Сейв хранит **только прогресс кампании**: корпус, кредиты, репутацию,
апгрейды, инвентарь, активное задание и где пристыкованы. Физическое состояние (позиции в комнатах,
EVA, пробоины, выработанные жилы, ход боя) сознательно **не** сохраняется — сейв всегда снимается в
момент стыковки, то есть в заведомо чистой ситуации, и загрузка просто возвращает экипаж на ту
станцию, а не пытается восстановить произвольный момент. `World` только поднимает флаг
`AutosavePending`; в файлы ходит `GameServer` — мир ничего не знает про I/O. Формат — JSON с
`Version`, запись через temp-файл + `File.Move` (прерванная запись не затирает хороший сейв), любые
ошибки чтения/записи глотаются: битый сейв = «начать заново», а упасть на рядовой стыковке хуже, чем
потерять прогресс. Экран выбора корабля получил `[C] Продолжить`; выбор корпуса стирает старый сейв.

**Воровство и арест** (`StationCrate.cs`, `World.StationCrime.cs`, `NpcKind.Security`). Реализует
§10 дословно: в каждом сервисном отсеке лежит ящик станции, `F` его крадёт; охранник стоит в
последнем отсеке (дальше всех от дока — у вора есть фора); если пройти мимо него с краденым, через
~1.5 сек срабатывает арест — **штраф, конфискация, минус репутация**, все три. Сопротивление
(`Space` с оружием в руках) поднимает тревогу, и охрана начинает стрелять в ответ; убийство охранника
стоит вдвое больше репутации, чем арест. Перестрелка переиспользует боевую модель абордажа
(`TryFirePersonalWeapon` теперь работает и на станции), а не заводит вторую. Между визитами ящики
восстанавливаются и охрана успокаивается — станция не ломается навсегда, она помнит игрока
репутацией.

**Важное следствие**: правило «Независимых ничем не сдвинуть» пришлось смягчить. Их нейтралитет
теперь **политический** (не участвуют в сваре Консорциум/Вольный флот, к ним ничего не «рикошетит»,
цены не меняются), но на то, что сделали лично им, они реагируют — иначе домашняя станция была бы
местом, где можно грабить бесконечно без последствий.

**Групповые встречи** (`GalaxyPoint.SquadronSize`, `World.Voyage.cs: HandleEnemyShipDestroyed`).
Сектор может держать эскадру: корабли выходят **по очереди**, `Enemy` остаётся «текущим
противником» — поэтому турели, ИИ, абордаж, `CombatPanel` не менялись вообще. Убил один — на его
место встаёт следующий, полный HP и со своим экипажем для абордажа; сектор считается взятым только
когда кончился последний, и именно тогда закрывается bounty-задание. Каждое убийство отдельно бьёт
по репутации владельца. Сложность карты теперь задаётся размером эскадры: Бета — 2 корабля,
Дельта — 3, остальные по одному.

**Тесты**: 145/145 (было 131, +14: 5 на сохранения, 6 на преступность, 3 на эскадры). 5 прогонов
подряд чистые.

**Грабли этой сессии**:
- **Ящик патронов в качестве добычи ломает игру.** `World.Interact.cs` при `CarryingAmmoCrate`
  перехватывает **любое** `F` под «зарядить турель» — укравший ящик патронов не мог ни сесть за
  штурвал, ни надеть скафандр, пока от него не избавится. Содержимое ящиков подобрано инертным
  (`Mineral`/`MedKit`/`WireSpool`/`FuelRod`), в коде оставлен комментарий почему.
- **Тест, возвращающийся со станции на корабль, обязан закрыть за собой внешний шлюз** — иначе
  корабль травит воздух и персонаж умирает на долгом пути к штурвалу.
- **`FireBowTurretUntilEnemyDefeated` против эскадры бесшовно переходит к следующему кораблю**
  (условие цикла — «HP врага > 0», а замена приходит с полным HP). Для наблюдения за тем, что
  происходит *между* убийствами, тесты бьют напрямую через `Enemy.ApplyDamage`; `WinBattleAt`
  зациклен, чтобы дочищать весь сектор.

### Сессия — навигация к станции и явная стыковка

Запрос пользователя: «сделай станции видными на карте, поставь метки чтобы было понятно где станция
даже если её не видно, и добавь станции шлюз, при подлёте к которому появляется кнопка стыковки».

**Док-порт вместо автозахвата.** Раньше стыковка происходила сама: подлетел на 3 юнита к центру
станции медленнее 2 — и ты пристыкован. Теперь у станции есть физический берт
(`Station.DockingPortPosition`, смещён на 7 юнитов по -X от центра — с той стороны, откуда приходит
корабль), а сама станция стала **твёрдой**: врезался в корпус (`StationHullRadius = 5`) — корабль
встал, пройти насквозь нельзя. Берт намеренно вынесен за этот радиус, так что «встать к шлюзу»
никогда не означает «протаранить станцию». Стыковка — осознанное нажатие: сервер выставляет
`CanDockNow` (рядом с бертом + скорость < 2), клиент по нему рисует кнопку **СТЫКОВКА** на панели
штурвала, нажатие шлёт `ClientCommand.DockPressed`. Случайно надрейфовать в док больше нельзя, и
весь подлёт стал читаемым. Пока кнопка не активна, в её слоте показывается расстояние до шлюза.

**Видимость станции.** Радар штурвала (`HelmPanel`) получил отдельный тип отметки
(`DrawTrackedBlip`): станция, её берт и — в бою — вражеский корабль. В отличие от астероидов они
**не пропадают** за пределами дальности радара, а прижимаются к его кромке со стрелкой наружу —
пеленг есть всегда, иначе ручной подлёт превращается в угадайку. В самом мире (`FieldRenderer`)
берт рисуется отдельно от корпуса станции и пульсирует зелёным ровно тогда, когда кнопка активна
(два индикатора всегда согласованы), плюс появились **указатели за краем экрана**
(`DrawOffScreenMarker`) — стрелка на кромке вьюпорта с расстоянием, отдельно для станции, для шлюза
и для врага.

**Тесты**: 149/149 (было 145, +4 на стыковку: близость сама по себе не стыкует, кнопка вдали не
работает, на скорости не срабатывает, корпус станции не пропускает корабль). 4 прогона чистые.

**Грабли**: тестовый хелпер `DockAtStation` пришлось переписать с «полный газ, потом стабилизация»
на **bang-bang-контроллер** (газ к берту, когда медленно; торможение, когда быстро). Наивная
последовательность даёт дедлок: торможение с полной скорости останавливает корабль **не доезжая**
до берта, и он висит там вечно.

**Полноэкранный режим.** Вся вёрстка клиента (начала панелей, вьюпорт, прямоугольники хит-тестов)
написана в фиксированных «дизайнерских» пикселях 1200×560. Вместо того чтобы делать всё это
резолюшн-независимым, сцена целиком рисуется в этом размере и **масштабируется** матрицей в
`SpriteBatch.Begin(transformMatrix:)` до реального разрешения экрана, с сохранением пропорций и
леттербоксом по краям — код вёрстки не тронут вообще. Окно — borderless на разрешении рабочего стола
(`HardwareModeSwitch = false`), так что alt-tab работает нормально и у монитора не запрашивается
экзотический режим 1200×560. **Единственное, что потребовало правок** — курсор: все хит-тесты
работают в дизайнерских координатах, поэтому позиция мыши один раз за кадр пересчитывается обратно
(`ToDesignSpace` → `_designMouse`), а не в каждом месте проверки. `F11` переключает обратно в окно.

**Грабли этой сессии** (в дополнение к списку выше):
- Тесты, которым нужно много боёв подряд, **обязаны надевать скафандр** — иначе персонаж умирает от
  декомпрессии накопленных пробоин задолго до конца, а мёртвый персонаж не дойдёт до штурвала.
- И **заходить на ремонт между боями**: урон копится (перерезанные провода, топливо, пробоины) до
  состояния, когда корабль физически не долетает до стыковки. Домашняя станция независима, так что
  заход туда ничего не искажает в измеряемой репутации.
- `FireBowTurretUntilEnemyDefeated` сдаётся после фиксированного числа циклов — «ровно 3 убийства»
  флейкует (засчитывается 2). Считать не попытки, а достигнутый порог, с запасом попыток.
- `DockAtStation` теперь делает до 3 заходов: сильно побитому кораблю может понадобиться и ремонт
  двигателя, и перебалансировка энергосети, и один проход это не всегда вытягивает.
- Руду **нельзя купить** для теста (цена 999 выставлена заградительно намеренно) — только реально
  добыть; вынесен общий хелпер `MineOre`.

### Внеплановая сессия — станции как физическое пространство + ручная стыковка

Прямой запрос пользователя: "сделай станции в виде отсеков, по которым можно ходить; попасть
пешком можно, пристыковавшись шлюзом к порту станции". Уточнено через `AskUserQuestion`:
(1) **несколько отдельных комнат** под каждого NPC, не один общий зал; (2) стыковка **ручная**,
через штурвал, не мгновенная. Реализует давно записанное в `game_design.md` §5/§10 ("станции тоже
модульные, как корабль, можно ходить по ним пешком после стыковки").

**Было**: станция — плоское меню. Прилёт к точке-станции мгновенно ставил `VoyagePhase.Station`
(чинил корпус, дозаправлял), а `StationPanel` рисовал полноэкранный оверлей с NPC-иконками в
собственной абстрактной системе координат (`StationNpc.X/Y`, `PixelsPerUnit=6`), никак не связанной
с интерьером. Класс `Station` содержал **только** список из 3 NPC, без единой комнаты.

**Стало**:
- `Station` (+ новый `Station.Default.cs`, по образцу `Ship.Scout.cs`) — настоящая физическая
  структура: 4 комнаты в ряд (`station-dock` / `station-trade` / `station-admin` /
  `station-workshop`), двери между ними, `ShipConnector` (тип `AirlockOuterDoor` — тот же приём
  "одна сторона реальная комната, другая вне структуры", что у корабля), фиксированная
  `Position` в world-space поля стыковки. `StationNpc.X/Y` сменили смысл на физические координаты
  внутри комнат станции.
- Новый `RoomLayout.cs` (Shared/Model) — алгоритм коллизии стен/дверей вынесен из
  `Ship.MoveAlongAxis` (та стала однострочным делегатом), `Station` использует его же. Без этого
  логика ходьбы дублировалась бы для второй структуры.
- Новая фаза `VoyagePhase.StationApproach` + `World.StationDocking.cs`: `Arrive` для станции теперь
  зовёт `EnterStationApproach` (корабль ставится на 20 юнитов строго по -X от станции, носом к ней,
  скорость 0 — намеренно прямолинейный, прощающий старт), физика подлёта переиспользует **тот же**
  штурвал/тягу/инерцию, что и поле астероидов (`World.ShipField.cs` разделён на
  `IntegrateShipFieldMotion` — общая интеграция — и отдельные обработчики "что происходит по
  прибытии" для каждой фазы). Попал в `DockCaptureRadius=3` на скорости `<DockMaxSpeed=2` —
  состыковался (`EnterStation`); влетел слишком быстро — **не** пробоина (корпус станции прочнее
  одинокого астероида, это не бой), просто гасится скорость прямо в зоне захвата, и следующий тик
  стыкует.
- Переход пешком: `TryCrossIntoStation`/`TryCrossBackToShip` в том же файле, вызываются из
  `StepCharacters` рядом с существующим `TryCrossIntoVacuum`. Используется **тот же самый**
  внешний шлюз корабля, что и для EVA — новых дверей на стороне корабля не добавлялось; скафандр
  **не** нужен (герметичный переходник, не вакуум), но требуется `Phase == Station`. Новое поле
  `Character.OnStation` (+ `CharacterState.OnStation` в протоколе) переключает, к какому набору
  комнат относится `RoomId`; `StepCharacters` роутит `MoveAlongAxis` на `Station` вместо `Ship`.
- Клиент: новый `StationRenderer` переиспользует `ShipRenderer`'s отрисовку комнат/дверей/
  персонажей (три метода стали `internal`), рисуя интерьер станции тем же визуальным языком.
  `Game1.ComputeStationCamera` — упрощённая параллель `ComputeCamera` (станция не двигается и не
  вращается, так что её локальные координаты и есть кадр камеры). Экстерьер станции виден из
  космоса в `FieldRenderer` тем же способом, что астероиды. `StationPanel` ужат до HUD-панели
  диалога (списки покупки/продажи/квеста/апгрейда без изменений), открывается кликом по **физически
  стоящему** NPC рядом; триггер по `AirlockConsole` убран целиком.
- **Экономику/квесты/апгрейды не трогали вообще** — они и раньше гейтились только на
  `Phase == VoyagePhase.Station`, без привязки к конкретному NPC.

**Сознательно не делали**: разные макеты станций по типу (§10 mining/trade/military/… — по-прежнему
один общий макет на все станции, ровно как раньше был один общий список NPC); бой/кража/арест на
станции; требование угла разворота при стыковке (только позиция+скорость); атмосфера/кислород в
отсеках станции (там всегда безопасно — `StepAtmosphere` пропускает `OnStation`-персонажей).

**Тесты**: 112/112 (было 106, +6: `RoomLayout_MoveAlongAxis_BlocksAtWallWithoutDoor`, прилёт даёт

### Внеплановая сессия — единая камера корабль/космос, паритет видимости

Прямой запрос пользователя после M15-M18: "чтобы космос и корабль находились в одном и том же
пространстве, без скрытых переходов, и видимость в космосе была такая же, как на корабле". До этой
сессии `ShipRenderer` (интерьер, `PixelsPerUnit=48`, статический `origin`, без учёта поворота
корабля) и `FieldRenderer` (космос, свой `PixelsPerUnit=6`, следящая камера, силуэт корпуса —
плоский повёрнутый прямоугольник) были двумя независимыми, переключаемыми по `IsOutside`
рендерерами; конус видимости скафандра (`VisionOverlay`, 5 юнитов/32°) применялся только внутри —
снаружи обзор был вообще ничем не ограничен. Пользователь через `AskUserQuestion` подтвердил: хочет
**точно такой же** конус и снаружи, осознанно принимая, что добыча руды/ориентация в открытом
космосе станут заметно сложнее на дистанции (было видно ~90 юнитов вокруг, стало ~5).

**Ключевой факт, упростивший задачу**: сервер уже трактует интерьер и поле астероидов как одно
физическое пространство — все внутренние объекты (`Room`/`Door`/`WallBlock`/`SystemDevice`/
консоли/персонажи с `IsOutside=false`) заданы в одной корабль-локальной системе координат, а
`ShipFieldState.Position/RotationDegrees` уже даёт положение/поворот этой системы в мировых
координатах поля. Для персонажей снаружи сервер уже сам резолвит их в готовые мировые X/Y
(`World.Eva.cs: GetEvaWorldPosition`) вне зависимости от того, к чему они прицеплены (корабль/
астероид/свободный полёт) — клиенту не нужно знать тип крепления, нужна только одна формула
конвертации мировая точка → корабль-локальная (новый `Client/Rendering/ShipLocalFrame.cs`:
`GetHullCenter`/`GetHullHalfExtents`/`ToLocal`, зеркалит `World.GetHullLocalBounds`/
`RotateWorldToLocal`).

**Архитектурное решение**: камера осталась **корабль-фиксированной** (интерьер по-прежнему рисуется
неповёрнутым на экране, как и раньше), а не мировой — иначе во время пилотирования/дрейфа мелкий
текст и клики по внутренним блокам (реактор, распределение энергии, проводка) вращались бы вместе
с экраном. Вместо этого при повороте корабля астероиды/космос визуально "плывут" вокруг
неподвижного интерьера — соответствует уже существовавшему design-комментарию в `FieldRenderer.cs`
про "pinned to the ship's own frame". Единая следящая камера (`Game1.ComputeCamera`) считает якорь
каждый кадр: внутри — сырая позиция персонажа, снаружи — та же позиция, прогнанная через
`ShipLocalFrame.ToLocal`. `_shipRenderer.Draw` теперь вызывается **всегда** (кроме отдельных
полноэкранных панелей — карта галактики/станция/проводка/штурвал, они не трогались), поверх —
`FieldRenderer` рисует внешние объекты в той же системе координат и с тем же `PixelsPerUnit=48`.
`FieldRenderer.DrawShip` (силуэт корпуса) удалён целиком — настоящие комнаты, которые и раньше
рисовал `ShipRenderer`, теперь всегда видны и играют роль корпуса, в том числе снаружи. Свечение
двигателя перенесено в отдельный метод `FieldRenderer.DrawEngineGlow`. `VisionOverlay.Draw`
вызывается один раз без ветвления по `IsOutside` — только по `WearingSuit`, как и раньше (снаружи
скафандр обязателен всегда, так что конус включается автоматически). Мышиный hit-testing
(`ShipRenderer.GetBlockRect`/`GetDoorRect` в `Game1.HandleMouseClick`) остался осепараллельным без
изменений в логике — просто получает каждый кадр новый `origin` от `ComputeCamera` вместо
константы `ShipOrigin`.

Статический `Game1.ShipOrigin`/`FieldViewportOrigin`/`FieldViewportSize` заменены одним
`WorldViewportOrigin`/`WorldViewportSize`.

**Проверено**: чистая сборка, 106/106 тестов (набор не покрывает клиентский рендер вообще, так что
это только защита от регрессий в серверной логике, которую это изменение не трогает), клиент
запущен и не падает при пассивном старте. **Не проверено интерактивно** — как и во всех предыдущих
сессиях, в этой песочнице нет инструмента для управления нативным MonoGame-окном (браузерные
инструменты работают только со встроенной веб-вкладкой); реальное прохождение шлюза/проверка
поворота камеры при пилотировании — на усмотрение пользователя при следующем живом запуске.

## Линия видимости и толстые стены

**Что просили**: игрок не должен видеть, что находится за стенами (в том числе внутри корабля),
через двери — должен; всё невидимое — абсолютно чёрное. Плюс стены толще и с деталями.

**Как сделано**. Старый `VisionOverlay` (затемнение на 0.85 альфы + веер полупрозрачных
прямоугольников на месте конуса) удалён — он не умел ничего перекрывать и не давал настоящей
черноты. На его месте два новых файла:

- `Rendering/Occluders.cs` — превращает набор комнат в плоский список отрезков стен (`WallSegment`,
  всегда осепараллельных), вырезая из них проёмы (`SightGap`) для **открытых** дверей. Закрытая
  дверь проёма не даёт — переборка перекрывает обзор ровно так же, как корпус (то же правило, что
  уже действует в движении, `RoomLayout.MoveAlongAxis`). Соседние комнаты дают два совпадающих
  отрезка на общей стене — это намеренно не дедуплицируется: для рейкаста ближайшее попадание всё
  равно одно, а склейка общих рёбер была бы заметно сложнее.
- `Rendering/VisibilityMask.cs` — полигон видимости обычным corner sweep'ом (по лучу на каждый угол
  стены плюс по чуть-чуть в обе стороны от него, чтобы граница тени попадала точно в угол, а не в
  ступеньку), плюс `ArcSamples` равномерных лучей, скругляющих внешний край света там, где стен нет.

**Ключевое решение — маска, а не тени поверх.** Полигон растеризуется белым по чёрному в
`RenderTarget2D` через `DrawUserPrimitives`+`BasicEffect` (`VertexColorEnabled`, вершинный цвет даёт
затухание к краю), а потом **умножается** на готовую сцену (`BlendState` с
`ColorSourceBlend = Zero, ColorDestinationBlend = SourceColor`). Умножение на ноль и есть та самая
абсолютная чернота — через альфу детали бы просвечивали. Рисовать тени фигурами поверх сцены нельзя:
тень отрезка — произвольная трапеция, а `SpriteBatch` умеет только повёрнутые прямоугольники.

**Ловушка с порядком в `Game1.Draw`**: смена render target'а сбрасывает содержимое бэкбуфера, поэтому
маска строится **до** `GraphicsDevice.Clear`. И блендинг задаётся в `SpriteBatch.Begin`, так что
`Draw` теперь состоит из трёх пакетов: сцена → `Composite` маски (свой `Begin/End` с умножением) →
HUD. HUD рисуется после маски и потому никогда не затемняется — отдельная область
`VisionDarknessArea` больше не нужна и удалена.

Глаз берётся из того же места, что и камера: внутри — позиция персонажа, снаружи — она же, свёрнутая
в систему координат корабля через `ShipLocalFrame.ToLocal` (`ComputeCamera` теперь возвращает третьим
полем `Anchor`). Иначе маска стояла бы там, где корабля нет. Радиус: в скафандре — прежний конус 5
единиц / 32°, без скафандра — 13 единиц кругом (комната освещается целиком, но не вся палуба).
Станция и абордаж используют свои комнаты/двери, для них `BuildVisibilityMask` возвращает `false`
только на полноэкранных панелях (карта/проводка/штурвал), где сцены нет.

**Стены**. `ShipRenderer.DrawRoom` разделён на `DrawRoomFloor` + `DrawRoomWalls`, и все три рендерера
(корабль, станция, абордаж) делают **два прохода** — сначала все полы, потом все стены. Иначе комната,
нарисованная позже, закрашивала бы своим полом плиту стены соседа: плита толщиной 12px центрирована
на границе комнат, то есть на 6px заходит внутрь каждой. Ширина выбрана меньше дверного проёма (1
единица = 48px), чтобы дверь по-прежнему чисто прорезала стену. Детали: светлая фаска изнутри,
тёмная снаружи, рёбра каждые 26px, кабель-канал по центру плиты (краснеет вместе с тревогой по
кислороду) и болтовые накладки на углах.

**Проверено**: чистая сборка, 149/149 тестов, и — впервые — **визуально**: клиент запущен в
полноэкранном режиме, ввод отправлен через `keybd_event` (P/Invoke из PowerShell; `SendKeys` не
работает, MonoGame читает сырое состояние клавиатуры, а не оконные сообщения), экран снят через
`Graphics.CopyFromScreen`. На скриншоте видно ровно то, что просили: комната игрока освещена целиком,
из дверного проёма идёт расширяющийся клин света в соседний отсек, всё остальное — чистый чёрный.

## Одна система координат: корабль, станция, космос

**Что просили**: (1) при стыковке корабль выравнивается и точно соприкасается шлюзовыми дверями,
(2) станция на карте выглядит по форме так же, как изнутри, (3) переход на станцию — без «перехода»,
как выход в космос.

**Ключевая идея, из которой следует всё остальное.** Раньше станция жила в собственных координатах,
никак не связанных с корабельными: переход был телепортом (`TryCrossIntoStation` ставил персонажа в
фиксированную точку `(1.5, 3)`), у станции была своя ветка камеры (`ComputeStationCamera`), а снаружи
она рисовалась кругом радиуса 5, не имевшим отношения к её планировке.

Теперь макет станции **строится вокруг корабельной двери**: `Station.Create(kind, connectorAnchor)`
получает позицию внешнего шлюза корабля в его же интерьерных координатах и кладёт свой
`ShipConnector` ровно туда. Стыковка (`TryDockAtStation`) обнуляет угол и ставит корпус на
`DockBerthPosition = Station.WorldOffset + hullCenter`. После этого мировые координаты и интерьерные
отличаются **ровно на `Station.WorldOffset`** — то есть корабль, станция и открытый космос
оказываются в одной системе координат, а два дверных прямоугольника совпадают до долей единицы (это
проверяет `World_Docking_MatesAirlockOntoStationConnector`).

Из этого следует остальное почти бесплатно:

- **Переход.** `TryCrossIntoStation`/`TryCrossBackToShip` удалены целиком. Пока пришвартованы,
  движение идёт по объединённой планировке (`GetDockedLayout`: комнаты корабля + комнаты станции,
  двери корабля + синтетическая `Door` **с тем же id**, что и внешний шлюз, + двери станции), и
  обычный `RoomLayout.MoveAlongAxis` сам переводит персонажа из отсека в отсек. `OnStation` теперь не
  переключатель режима, а **следствие** того, в какую комнату шагнули.
- **Камера и рендер.** Ветка `OnStation` в `Game1.Draw` убрана: интерьер станции рисуется тем же
  `origin`, что и корабль, рядом с ним, а не вместо него. Маска видимости при стыковке берёт
  окклюдерами комнаты корабля **и** станции — свет из корабельного шлюза честно падает в
  стыковочный отсек.
- **Форма снаружи и на радаре.** `FieldRenderer.DrawStationExterior` рисует реальные комнаты
  (`StationRooms + StationWorldOffset` → `ShipLocalFrame.ToLocal`), а не круг; при повёрнутом
  корабле они выходят повёрнутыми, поэтому нужны `Draw` с углом и `DrawRotatedOutline` (у
  `SpriteBatch` нет обводки повёрнутого прямоугольника). Радар штурвала плотит те же комнаты.
  Столкновение при подлёте теперь тоже по настоящему footprint'у и по четырём углам корпуса, а не
  «центр корабля vs круг».

**Ловушки, на которые напоролся.**

1. `CanDockNow` мерил расстояние от **центра** корабля до шлюза станции. Теперь центр обязан стоять
   на пол-корпуса дальше, так что метрика заменена на расстояние до `DockBerthPosition`; иначе
   тестовые хелперы вели корабль носом внутрь станции. Снапшот получил отдельное поле
   `DockBerthPosition`, панель штурвала показывает «До причала», а не «До шлюза».
2. Макет станции зависит от корпуса, а корпус можно **купить**. `_stationsByKind` перестал быть
   инициализируемым полем и пересобирается в `InitializeShipState()` — единственном месте, через
   которое проходят все три пути замены корабля (конструктор, загрузка, покупка). Id комнат/дверей
   от якоря не зависят, так что плоский словарь состояний дверей переживает пересборку.
3. `EnterStation` тоже ставит корабль на причал, а не только `TryDockAtStation` — иначе стартовое
   состояние игры (уже пристыкованы к домашней станции) рисовало бы экстерьер станции не там.
4. Отшвартовка с человеком на станции оставляла его в геометрии, которая больше ни к чему не
   присоединена — `TryStartTravel` затягивает всех обратно в шлюзовую камеру.
5. **Найденный побочный баг**: чтобы выйти на станцию, нужно открыть внешний шлюз — и корабль начинал
   травить воздух, потому что `StepAtmosphere` считал эту дверь всегда открытой в вакуум. У
   пристыкованного корабля за ней герметичный отсек станции, так что при `Phase == Station` утечки
   нет. Три существующих теста на разгерметизацию стартовали в доке и полагались на старое поведение
   — им добавлен `CastOffIntoSpace`.

**Проверено**: чистая сборка, 153/153 теста (4 новых: точное сопряжение, непрерывность перехода,
эвакуация при отшвартовке, отсутствие утечки в доке) и визуально в живой игре — проход из шлюза
корабля в отсеки станции одним непрерывным движением без смены вида, и станция на радаре штурвала
как вытянутый блок отсеков, а не точка.

## Выход в космос: ботинки по обшивке и прыжок по курсору

**Что просили**: в магнитных ботинках ходить вплотную по корпусу, а не «непойми где» в двух метрах
от него; отпрыгивать туда, где курсор, а не «непойми куда».

### Прыжок не туда — общая ошибка системы координат

Причина оказалась не в самом прыжке, а в том, **в какой системе координат клиент шлёт направления**.
Снаружи камера рисует всё в собственной (неповёрнутой) системе корабля — значит и WASD, и вектор
«от игрока к курсору» приходят в ней. А EVA-физика сервера (`StepFreeFloating`, `HandlePushOff`,
движение по астероиду) работает в мировых координатах поля; `StepShipAttachedWalk` даже явно делает
`RotateWorldToLocal`, то есть сервер **последовательно ожидает мировое** направление. Клиент слал
экранное. Пока корабль не повёрнут, разницы нет — стоит его развернуть, и прыжок, и ходьба уезжают
на угол корабля.

Починка одна и на клиенте: `ShipLocalFrame.ToWorldDirection` / `ToLocalDirection` (только поворот,
без переноса), и в `Game1.Update` при `isOutside` через неё прогоняются **и** `move`, **и**
`pushOffDirection`. Туда же попал третий случай той же ошибки: `CharacterState.Facing*` снаружи
мировой, а маска видимости строится в системе корабля — в `BuildVisibilityMask` направление конуса
теперь конвертируется обратно.

### Ботинки

`ClampToShipZone` только **ограничивал** смещение коробкой «корпус + 2 единицы». То есть внутри этой
коробки можно было гулять где угодно — в двух метрах над обшивкой и даже поперёк середины корпуса,
где под ногами ничего нет. Плюс `EvaExitNudge = 1f` отталкивал от двери на целую единицу в пустоту.

Теперь смещение **проецируется на контур** корпуса (`SnapToHullSurface`): точка внутри контура
выталкивается через ближайшую грань, точка снаружи — притягивается к ближайшей точке контура.
Отступ `HullWalkClearance = 0.35` — половина ширины персонажа, то есть скафандр касается обшивки.
Шаг «в корпус» держит на грани, шаг вдоль — скользит, шаг за угол — переводит на соседнюю грань.
То же для астероида (`SnapToAsteroidSurface`), и то же при автоприцепе `TryAutoAttach` — зона захвата
осталась широкой (2 единицы, поймать корпус должно быть легко), но встаёшь ты всегда на обшивку.

**Ловушка**: без выталкивающего нуджа персонаж после выхода стоит **прямо на прямоугольнике двери**,
и проверка «стою в двери → вернуться внутрь» затягивала обратно при первом же шаге вдоль корпуса.
Добавлено условие «шаг именно **внутрь**». Первая версия мерила расстояние до центра корпуса — и
провалилась на тесте: скольжение вдоль грани к середине корабля уменьшает радиус, ни на сантиметр
не приближая к обшивке. Правильная мера — расстояние до **контура** (`HullSurfaceDistance`), оно при
скольжении вдоль грани не меняется.

**Проверено**: чистая сборка, 155/155 тестов (2 новых: походка держит контур при обходе всех граней
и угла; шаг от двери вдоль корпуса не роняет обратно в шлюз). Поворот направлений на клиенте
тестами не покрыт — в тестовом проекте нет ссылки на клиентскую сборку.

**Обзор в скафандре расширен.** Конус нашлемного фонаря был 5 единиц / 32° — работать в нём (майнить,
заходить в шлюз) практически нельзя. Стало 9 единиц / 55°, плюс отдельная всенаправленная «лужа»
подсветки радиусом 3 (`SuitAmbientRadius`), чтобы то, что стоит вплотную сбоку, не было невидимым.
Технически `VisibilityMask.Build` теперь складывает **два** полигона видимости в одну маску
(`AddLightPolygon` вызывается дважды, `_vertexCount` не сбрасывается между ними, `Grow` перешёл на
`Array.Resize`), а растеризация — `BlendState.Additive` вместо `Opaque`: иначе второй полигон
опускал бы перекрытие до своей, более тусклой яркости. Для одиночного полигона (без скафандра)
поверх очищенной в чёрный цели additive ведёт себя ровно как opaque, так что этот путь не изменился.

## Стеллаж и перетаскивание предметов мышью

**Что просили**: перетаскивать предметы между слотами инвентаря курсором, и стеллаж на корабле на 30
предметов.

**Одна операция вместо трёх.** Ключевое решение — не делать «положить на стеллаж», «взять со
стеллажа» и «переложить в рюкзаке» тремя разными командами. Введён `SlotRef(ItemSlotKind, Index)`
(`Shared/Protocol`), команда — одна пара `MoveItemFrom`/`MoveItemTo`, сервер (`World.Storage.cs`)
просто **меняет содержимое двух слотов местами**. Обмен, а не перезапись: промахнуться мимо пустого
слота и уничтожить единственный резак — слишком дорогая цена за неточное движение мышью.

Доступ к слоту стеллажа требует стоять у него (`InteractionRadius`) — это полка, а не карман;
перекладывать в собственном ряду можно где угодно. Всё, что переехало, **выпадает из рук**: список
`HeldSlotIndices` хранит индексы слотов, и тихо переуказать его на то, что приехало в этот слот,
было бы хуже, чем просто положить предмет.

**Стеллаж.** `StorageRack` — модель по образцу `SuitLocker`; `Capacity = 30`. Один на корабль, у
каждого класса в своей комнате (фрегат — каюты, крейсер — трюм, разведчик — машинное). Содержимое
живёт в `World` и **переживает смену корпуса**: груз принадлежит экипажу, молча списывать его при
апгрейде корабля — неприятный сюрприз. Попало в сохранение (`SaveGame.RackSlots`, версия файла
1 → 2; старые файлы читаются как пустой стеллаж).

**Клиент.** `RackPanel` рисует 30 слотов **тем же** `InventoryPanel.DrawSlot` (он стал
`internal static`) — две разные по виду сетки читались бы как две несвязанные системы. Перетаскивание
живёт в `Game1.UpdateItemDrag`: нажатие на непустой слот начинает драг, отпускание над слотом шлёт
команду, отпускание мимо — возвращает предмет на место.

**Ловушка**: нажатие — это же событие, на котором висит `HandleMouseClick`, и его ветка «клик по
пустому месту закрывает панель» закрывала бы стеллаж при попытке взять из него предмет. Поэтому драг
получает право первого отказа: если нажатие попало в слот, клик в этот кадр не обрабатывается вообще,
а `_prevLeftMouseButton` обновляется вручную, чтобы детектор фронта в `HandleMouseClick` не разъехался.

**Ловушка в тестах**: `MoveCharacterTo` ведёт персонажа сразу по обеим осям и втыкается в переборку,
если цель не на общей высоте дверей. Добавлен `WalkAcrossShipTo` — сначала на ряд дверей, потом
поперёк корабля, потом шаг в сторону.

**Проверено**: чистая сборка, 160/160 тестов (5 новых: укладка на стеллаж, обмен при попадании в
занятый слот, отказ вдали от стеллажа, перекладывание в своём ряду с очисткой рук, круг сохранения).

## Двойной клик по предмету и заряд стержней

**Двойной клик = быстрый перенос.** В `Game1.UpdateItemDrag` нажатие на непустой слот теперь сначала
проверяется на второй клик по тому же слоту в пределах `DoubleClickSeconds` (0.4 c). Если да —
`QuickMoveTarget` ищет **первый свободный** слот в противоположном контейнере и шлётся та же самая
пара `MoveItemFrom/MoveItemTo`, что и у перетаскивания: сервер по-прежнему знает ровно одну операцию
«поменять два слота местами», клиент лишь сам выбирает адрес. Работает только при открытом стеллаже —
иначе «на ту сторону» не имеет смысла. Стеллаж полон (или ряд полон при переносе обратно) — не
делается ничего: подменить произвольный занятый слот хуже, чем не сработать.

`_lastSlotClickSeconds` после срабатывания сбрасывается в `-∞`, иначе тройной клик уехал бы вторым
переносом ещё до прихода нового снапшота.

**Топливо переехало внутрь стержней.** Раньше `Reactor` держал общий бак `Fuel`, а `RodSlots` были
`bool[]` — «есть стержень / нет». Из-за этого свежий стержень с рейки ничего не давал: бак-то пустой,
и стержни ощущались разряженными. Теперь `Reactor.Rods` — `float?[4]`: `null` — пустой слот, иначе
остаток заряда в стоящем там стержне; `Fuel` — просто сумма загруженного, `MaxFuel` сохранил смысл
(полный комплект), чтобы HUD не менялся. `InsertRod` кладёт стержень **полным** — стержни с рейки
бесконечны и новые, так что донести стержень до реактора и есть акт дозаправки. Горят по одному
подряд, а не все сразу, поэтому в панели видно, какой именно сдох. `Refuel()` на станции заряжает
только те стержни, что реально стоят в реакторе.

Остаток вынутого наполовину стержня не сохраняется: слот инвентаря хранит *тип* предмета, а не
экземпляр. Формально это позволяет «обновить» стержень вынул-вставил, но рейка и так выдаёт
бесконечно новые — терять на этом нечего.

**Панель реактора** рисует корпус стержня всегда, а заряд — заливкой снизу (зелёный → оранжевый →
красный), пустой слот и сдохший стержень должны выглядеть по-разному, иначе «замени мёртвый» не
читается как инструкция. Протокол: `ReactorState.RodSlots` (bool) → `RodCharges` (`float?`, доля 0..1).

**Проверено**: чистая сборка, 163/163 теста (4 новых: сгорание по одному стержню, полный заряд
свежего стержня в выгоревший слот, обнуление выработки при вынутых стержнях, оживление мёртвого
реактора принесённым стержнем). Двойной клик — чистая клиентская логика, тестами не покрыт.

**Раскладка HUD инвентаря.** Ряд переносимых слотов теперь по центру нижней кромки, слоты экипировки
(наушники/одежда/головное) — в правом нижнем углу; размер слота 26 → 34. Разделены потому, что ряд
меняется каждые несколько секунд, а экипировка — раз в час, и держать их одним блоком значило отдать
центр экрана тому, на что почти не смотрят. Обе точки считаются от края экрана
(`InventoryRowOrigin(slotCount)`, `EquipSlotsOrigin`) через `InventoryPanel.RowWidth/RowHeight`, а не
заданы числами: иначе каждое изменение размера слота приходилось бы догонять правкой координат.
Ширина ряда зависит от числа слотов, поэтому origin — функция от снапшота, и хит-тесты
(`HitTestItemSlot`, полоски удержания) берут ту же функцию, а не свою копию координат.

Ряд намеренно опущен **ниже нижней кромки дизайн-области (560)** — в чёрную полосу леттербокса:
на 16:9 дизайн-область заканчивается заметно выше физического низа экрана, и ряд, упёршийся в неё,
читается как висящий посреди экрана. `LetterboxBelowDesign = _renderOffset.Y / _renderZoom` даёт,
сколько этой полосы есть в дизайн-пикселях; на окне, которое леттербоксится по бокам, оно равно нулю
и раскладка сама сводится к «у нижней кромки». Клипа по дизайн-прямоугольнику нет, `ToDesignSpace`
тоже отдаёт Y > 560, так что и рисование, и клики за кромкой работают.

## Станция только там, где она есть, и «руки» в слотах

**Станция в чужом секторе.** `World` всегда держит объект `Station` — это макет, с которым стыкуешься,
— и `FieldRenderer` рисовал его экстерьер, стыковочный порт и оба off-screen-маркера в любой фазе,
кроме `Station`. В итоге при спавне во вражеском секторе или в поясе астероидов посреди боя висела
дружественная станция со «Шлюзом». Добавлен `VoyagePhases.HasStationInField()`
(`StationApproach | Station`) в `Shared/Model/VoyagePhase.cs`, и **все** виды, которые наносят
станцию (`FieldRenderer`, радар `HelmPanel`), спрашивают его — иначе они разойдутся при следующей
новой фазе. Серверная сторона правки не потребовала: коллизия с корпусом станции и так живёт только
в `StepStationApproachPhysics`, а `CanDockNow` гейтится на `StationApproach`.

**Индикаторы рук.** Как в Barotrauma: в слоте предмета рисуется столько миниатюрных ладоней, сколько
рук он требует (`ItemDefinitions.HandsRequired` — 1 у ключа/резака/стержня, 2 у сварочного аппарата
и стволов). Тускло, пока предмет просто лежит в ряду, и зелёным, когда он реально в руках, — так
вопрос «почему не берётся резак» отвечает сам себя, когда рядом горят обе руки двуручного сварочника.
Глифы рисует `InventoryPanel.DrawHands/DrawHand` из того же единственного белого пикселя: ладонь,
три пальца и большой палец сбоку, зеркальный у правой руки — минимум, который ещё читается как рука
на 8×9 пикселях. Полоска удержания под слотом осталась: она — кликабельная цель для взять/положить,
а руки только показывают состояние.

## Бой: эскадры в поле, снаряды, пушки на корпусе

Раньше бой был полосой HP и таймером: `EnemyShip` — «абстрактный общий HP без позиции»,
`StepEnemyAi` раз в 6 секунд бросал кубик и портил что-нибудь на корабле, а выстрел из турели
мгновенно вычитал урон из этого HP откуда угодно — хоть с пристыкованной станции. Промахнуться было
нечем, потому что снаряда не существовало.

**Эскадра в поле.** `World.EnemyFleet.cs`: весь отряд сектора (`GalaxyPoint.SquadronSize`) висит в
поле **одновременно**, каждый корпус — `EnemyShipRuntime` со своей позицией, скоростью, HP и
перезарядкой. `World.Enemy` стал вычисляемым — это первый живой корабль, тот же «один враг», который
нужен полосе HP, экипажу и абордажу; убил его — место занимает следующий. Поэтому старая
последовательность «убил → пришёл следующий» и её тесты уцелели, просто остальные уже на доске.

Строй считается **от оси корпуса игрока**, а не от текущего пеленга. Первая версия целилась в точку
«на дистанции 22 по той линии, на которой я уже нахожусь» — этому уравнению удовлетворяет вся
окружность, и отбившийся ведомый вставал на фланге навсегда и не подходил под выстрел. Теперь линия
огня строится на кормовой четверти игрока и едет вместе с кораблём, а боковое смещение
пересчитывается **по живым**, так что строй смыкается по мере потерь.

**Снаряды.** `World.Projectiles.cs` — общий список для обеих сторон. Шаг считается **отрезком**
от прошлой позиции к новой, а не точкой: лазерный болт на 44 юнитах в секунду иначе протыкает корпус
между тиками. Отрезок проверяется против астероидов (камень глушит всё, чей бы выстрел ни был),
корпуса игрока и корпусов врага. Прилёт вражеского снаряда зовёт `ApplyEnemyAttack()` — тот самый
разбор «щит → турель → перерезанный провод → пробоина», что был в таймере; последствия те же, но
теперь их вызывает что-то, что долетело и могло не долететь. Огонь открывается только при прямой
видимости (`HasLineOfSight`), поэтому спрятаться за астероид впервые имеет смысл.

**Пушки снаружи.** `TurretMount` (Shared) считает точку установки из габаритов корпуса, а не хранит
её в определении турели — новый класс корабля получает мосты бесплатно. Все стволы на кормовой
плите, равномерно по высоте: рейдеры подходят с кормы, и шлюз для абордажа там же, так что пушки,
враг и выход смотрят в одну сторону; `+-45` где-нибудь ещё смотрели бы весь бой в пустоту. Перископ
внутри комнаты остался отдельной вещью — это место экипажа, а линия прицеливания раньше шла из
консоли, будто корабль стреляет собственной мебелью.

**Ловушка с геометрией**: дистанция удержания меряется от **центра** корпуса, а полукорпус стартового
фрегата — 13 юнитов. С прежними 12 враг «держался» внутри корабля, по которому стрелял, а дуло
оказывалось у него за спиной. Отсюда 22.

**Видимость в турели.** Стрелок за перископом смотрит сквозь корпус: маска снимается целиком, как у
штурвала. Побочный эффект — свои стволы видно только из турели, из штурвала или снаружи в скафандре:
для всех остальных это пространство за стеной, то есть чернота.

**Карта капитана** рисует все живые корпуса (жёлтым — отступающие) и снаряды в полёте; поле —
корпуса с полосой HP и носовым блоком, плюс off-screen-пеленги на каждого.

**Ловушка в тестах**: турель надо занимать **до** входа в сектор. Прилёт вражеского снаряда с шансом
0.35 выводит турель из строя, и тест, который шёл к пушке уже под огнём, разваливался через раз.
Плюс `StepFor` — «выстрелил и посмотрел HP на следующем тике» больше не работает, снаряду нужно
долететь.

**Проверено**: чистая сборка, 166/166 (3 новых: эскадра появляется в поле и сближается, отрезок
против астероида как укрытие, снаряд мимо при отвёрнутом стволе; 6 старых переписаны под бой в
секторе). Визуально бой не снимал — нет способа доехать до него скриптом ввода без долгой возни с
кликами по карте.

**Перископ и наводка мышью.** Первая версия пушек была неиграбельной: ствол на кормовой плите,
перископ — в носовом кокпите, а камера как и раньше следила за человеком. Стрелок смотрел в стену в
26 юнитах от собственного орудия и не видел ни ствола, ни того, во что стреляет; наводка A/D
работала, но без обратной связи выглядела как «ничего не происходит».

Теперь при занятии турели камера уходит **на ствол** (`ComputeCamera` берёт якорь у `TurretMount`
плюс `PeriscopeViewLead` наружу) — это и есть перископ. Наводка идёт **на курсор**: клиент считает
угол от установки до курсора, зажимает его в дугу турели и шлёт **направление доворота**, а не
готовый угол, — сервер остаётся единственным, кто решает, как быстро ствол поворачивается
(`TurretAimRateDegreesPerSecond`) и куда он вообще может смотреть. A/D оставлены как запасной
вариант и имеют приоритет, когда нажаты. Занятая турель рисуется толще, с краями дуги обстрела,
линией прицела из дула и градусами у основания.

**Краш при заходе в турель — шрифт, а не логика.** `DebugFont.spritefont` покрывает ASCII, кириллицу
и общую пунктуацию; знак градуса (U+00B0), который я поставил в подсказку наводки и в надпись у
основания ствола, в регионы не входил, а `SpriteBatch.DrawString` на отсутствующем глифе не рисует
«?», а **бросает исключение** — то есть игра падала ровно в тот кадр, когда кто-нибудь садился за
пушку. В файле уже висел комментарий, что это же однажды случилось с длинным тире. Теперь добавлены
`<DefaultCharacter>?</DefaultCharacter>` (промах по глифу — косметика, а не повод ронять игру) и
регион Latin-1, чтобы градус рисовался как градус.

**Обзор из турели, крыша и столкновение корпусов.**

*Дальность.* Занятая турель отводит всю сцену на половинный масштаб (`SceneZoom`, `TurretViewZoom
= 0.5`) — вдвое дальше видно. Масштаб приложен **одной матрицей ко всему пакету сцены**, а не
параметром в каждый рендерер, поэтому камера, мир и хит-тесты не могут разъехаться. Но за это надо
платить в трёх местах: начало камеры делится на зум (якорь должен попасть в центр экрана *после*
масштабирования), viewport для off-screen-маркеров тоже (кромки экрана живут по ту сторону масштаба),
и `ReadTurretAimTowardCursor` переводит установку в дизайн-координаты через тот же зум — иначе курсор
и ствол расходятся во мнении, где «вон там».

*Крыша.* Из-за перископа игрок физически снаружи, поэтому `ShipRenderer.Draw(hullPlating: true)`
рисует корабль закрытым: сплошная плита по габаритам комнат с теми же рёбрами и кромками, что у
переборок, плюс турели поверх. Интерьер, экипаж и мебель не рисуются вовсе — иначе корабль читается
как открытый план, висящий в космосе. Пристыкованная станция по той же причине рисуется **экстерьером**
(`FieldRenderer.Draw(seenFromOutside: true)`), а не интерьером: без этого рядом с кораблём зияла бы
чёрная дыра там, где станция.

*Мышь.* Пока турель занята, `HandleMouseClick` уходит в no-op целиком: сцена сдвинута к пушке и
уменьшена вдвое, так что все мировые хит-тесты указывали бы на то, что было под курсором раньше.

*Столкновения.* Корпуса больше не проходят друг сквозь друга. `SeparateEnemy` после каждого шага
выталкивает рейдера из ориентированного бокса корабля игрока (а вырожденный случай «центр внутри
бокса» — через ближайшую грань) и разводит рейдеров между собой; `StepShipFieldPhysics` через
`HullOverlapsEnemy` останавливает сам корабль игрока перед вражеским, без пробоины: таранить —
не тактика, а обшивка у них не хуже нашей.

**Проверено**: 167/167 (новый — `World_Battle_ShipsDoNotOverlapWhenTheyCollide`: полный ход в
рейдера, корпус встаёт перед ним, а не в нём) плюс живой запуск: перископ, крыша, наводка по курсору.

## Корвет: первый корабль с вертикальной компоновкой

Новый класс `ShipKind.Corvette` (`Ship.Corvette.cs`), выбирается клавишей **4** на экране выбора.
Все прежние классы — ряд коробок вдоль X; этот идёт **сверху вниз**: кокпит → оружейная →
реакторный отсек → шлюзовая камера по хребту, а от реакторного отсека вбок отходят два длинных
отсека — щитовая слева, жизнеобеспечение справа, у каждого свой двигатель в самом низу. Шесть
отсеков.

Добавлять новый класс, а не переделывать фрегат, — сознательно: половина тестов ходит по фрегату
на жёстко зашитых координатах, и переписывать их ради новой планировки значило бы менять то, что
проверено, ради того, что ещё нет.

**Первые горизонтальные двери.** Хребет соединён дверями-щелями поперёк (`Width: 1.8, Height: 1.0`).
`RoomLayout.MoveAlongAxis` оказался к ним готов — он проверяет прямоугольник двери, а не ось, — но
раньше это никем не использовалось, поэтому на всякий случай есть тест, который прогоняет персонажа
через весь хребет и в оба боковых отсека.

**Бортовой залп.** У турели появилась `MountSide` (`Aft` по умолчанию — прежнее поведение всех
классов). Раньше сторону выводили из геометрии корпуса, и это работало ровно до первого корабля,
которому нужны пушки на флангах: у корвета обе пушки стоят на противоположных стенах оружейной и
стреляют наружу через её же плиты. Место установки для `Port`/`Starboard` берётся от стены **своей
комнаты**, а не от габаритов корпуса, — иначе ствол вылезал бы посреди обшивки там, где боковые
отсеки шире хребта. Рейдеры держатся у правого борта (`World.EnemyFleet.cs` строит линию по
локальному +X), так что правая пушка — рабочая, левая — на разворот.

**Два стыковочных порта**, по одному на внешней стене каждого бокового отсека: стыковаться можно
любым бортом. `Station.Create` по-прежнему привязывается к `AirlockOuterDoors.First()` — правому.

**Два двигателя.** `system-engine-2` пришлось добавить **всем** классам: топология проводки одна на
все корпуса, и корабль без второго блока оставил бы `drop-engine-2` висеть в пустоту — а правило
«потеря одного дропа из пары стоит половины мощности системы» тогда штрафовало бы его за поломку
устройства, которого у него нет. Заодно это ровно то же, что уже сделано у щитов.

**Размеры.** `ReactorBlock` и `ShipSystemDevice` получили `SizeScale` (по умолчанию 1): реактор
корвета в 2.6 раза больше обычного и стоит в нижней части зала, двигатели — в 2.4. Отсек, построенный
вокруг реактора, должен и выглядеть так.

**Обшивка по отсекам.** `DrawHullPlating` рисует закрытый корпус покомнатно, а не одним
прямоугольником по габаритам: у корвета хребет уже боковых отсеков, и общий прямоугольник делал вид,
будто пушка растёт из середины плиты. Перископ турели при закрытом корпусе не рисуется — это
внутренняя мебель.

**Проверено**: 169/169 (2 новых — состав/пушки/порты корвета и проход по всему хребту) плюс живой
запуск: кокпит, ход вниз по хребту, вид из правой турели с обеими пушками на флангах.

## Пульт капитана: карта, монитор отсеков, поведение штурвала

**Карта.** Радар вырос с 90 до 150 пикселей радиуса при той же дальности (50 юнитов) — то есть стало
не дальше видно, а подробнее. Свой корабль рисуется схематично: каждый отсек своим прямоугольником,
повёрнутым на текущий курс, пробитые — красным. Стрелка говорила только «куда смотрит нос», а схема
отвечает на вопрос, который капитан на самом деле задаёт: с какого борта заходит рейдер. Станция на
этом же радаре так рисовалась и раньше — теперь одинаково.

**Монитор отсеков** (`ShipStatusPanel`, отдельный файл) — справа от радара: строка на отсек, полоса
кислорода, число пробоин, отказавшие системы. Цвет по худшему: пробоина важнее низкого O2, низкий O2
важнее сдохшей коробки — в том порядке, в каком с ними приходится разбираться. Всё это видно и так,
если дойти ногами, но капитан в манёвре как раз никуда дойти не может.

**Штурвал не хватает чужие клики.** Раньше `UpdateHelmThrustDrag` ставил вектор тяги при **любом**
зажатии мыши у штурвала, где бы ни был курсор, — включая нажатие на саму кнопку «Стабилизация»,
которая тем самым в том же кадре давала полную тягу в свою сторону. Теперь ручка отзывается только
на нажатие, **начавшееся** внутри круга; начатый драг можно уводить за круг — вектор просто упирается
в обод, как настоящая ручка в упор.

**Ловушка: стабилизация не держалась.** Починка выше вскрыла, что кнопка не работала вообще.
Сервер понимает `HelmStabilizePressed` как команду на один тик, а уже следующий кадр присылает
сохранённый вектор ручки — и это считается новым вводом пилота, который стабилизацию отменяет
(`SetHelmThrust` всегда сбрасывает `_shipAutoStabilize`, даже для (0,0): «ручка в центре» — это не
«тормози»). Поэтому клиент теперь **защёлкивает** режим: шлёт его каждый кадр, пока не тронут
штурвал, и сразу ставит ручку в центр, чтобы индикация совпадала с тем, что делают двигатели.

**Проверено**: 169/169, живой запуск — радар со схемой корвета, монитор всех шести отсеков, ручка
не дёргается при клике по кнопке. Защёлку стабилизации подтвердить скриншотом не вышло: захват
экрана снова поймал чужое окно.

**Корвет уменьшен на ~30%.** 20x27 юнитов → 13.5x18.5, планировка та же. Масштабированы и блоки:
реактор 2.6 → 1.8, двигатели 2.4 → 1.7 — они задаются в пикселях, а не в юнитах, так что без этого
уменьшенные отсеки оказались бы забиты прежней по размеру мебелью, то есть изменился бы не только
масштаб. Границы комнат легли на половины юнита, чтобы поюнитные блоки обшивки оставались ровными.
Тест прохода по всему хребту переведён на новые координаты — он и есть проверка, что раскладка не
рассыпалась.

## Корвет: нос вперёд, двигатели снаружи, шлюзы починены

**Летит носом.** Поворот корпуса всегда выставлялся так, чтобы вдоль скорости смотрела локальная ось
+X. Для рядных корпусов это незаметно, а корвет из-за этого летел боком. У `Ship` появилось
`ForwardDegrees` — куда у этого корпуса «вперёд» в его собственных координатах (0 у рядных, -90 у
корвета), и `IntegrateShipFieldMotion` вычитает его из целевого угла. Всё остальное по-прежнему живёт
в неповёрнутом корабельном фрейме — меняется только выбор угла.

**Двигатели снаружи.** `DrawEngineGlow` (одно пятно на фиксированной точке) заменён на `DrawEngines`:
по гондоле на каждый **реально существующий** блок двигателя, посаженной на ближайшую к нему плиту
корпуса снаружи, соплом наружу. Позиция читается из `SystemDevices`, поэтому корабль с двумя
двигателями показывает два — в тех отсеках, где они установлены. Пламя мерцает (фаза сдвинута по id,
чтобы пара не пульсировала синхронно) и горит только в фазах, где корабль реально летит: тяга,
заданная у причала, ничего не двигает, и подсвеченные сопла у стыковочного узла были бы враньём.

**Шлюзы корвета не открывались.** `TryCrossIntoVacuum` требовал, чтобы персонаж стоял в комнате с
именем `"airlock-chamber"`. У корвета порты врезаны в боковые отсеки — экипаж был заперт внутри
навсегда. Теперь проверяется дверь, врезанная **в ту комнату, где стоит персонаж**, и возврат
внутрь кладёт его в комнату этой же двери, а не в комнату с волшебным именем.

**Отсек под реакторным убран** (осталось 5), шкафы со скафандрами переехали к самим портам — по
одному в каждый боковой отсек, чтобы одеваться там, где выходишь, а не через весь корабль. Стеллаж
переехал в реакторный зал. Боковые отсеки теперь выступают за хвост хребта — корма корабля стала
парой двигательных пилонов.

**Проверено**: 171/171 (3 новых: выход через бортовой порт, полёт носом вперёд, скафандры у портов).

## Скафандр и астероиды: семь правок одной области

**Силуэт вместо габаритов.** Всё, что происходило снаружи корабля, считалось по прямоугольнику
min/max всех комнат. На рядных корпусах это одно и то же, но корвет — буква П, и ботинки ходили по
пустоте между двигательными пилонами. Новый `HullSilhouette` (Shared) отвечает на три вопроса —
внутри ли точка, как далеко она от обшивки и куда её поставить — по **объединению комнат**. На нём
теперь ходьба на магнитах, зона захвата и столкновение корпуса. Выход через внешний угол стал
поворотом вокруг него на постоянном расстоянии, а не «клампом по осям» — старый тест это и ловил,
переписан на честный инвариант «стою ровно на клиренсе от обшивки».

**Астероид — многоугольник.** `AsteroidShape` строит замкнутый контур из радиусов, разбросанных по
углам и один раз сглаженных, детерминированно из id. Один и тот же контур теперь у физики и у
картинки: раньше камень выглядел рваным, а сталкивался идеальным кругом. Хеш выписан руками —
`string.GetHashCode` рандомизируется на каждый запуск процесса, и рок бы менял форму между сессиями.
Рудные жилы прописаны точками на номинальной окружности и **проецируются на реальный контур** при
сборке пояса, иначе жила оказывается внутри выступа или висит над выемкой и до неё не дотянуться.

**Прыжок больше не проходит сквозь всё.** Отталкивание давало 3 секунды полной неуязвимости к
притяжению — за это время можно было пролететь насквозь и камень, и собственный корабль. Теперь
держится не время, а **личность того, от чего оттолкнулся**: именно он не ловит, пока не отлетишь на
запас, а всё остальное ловит сразу. Плюс притяжение проверяется **вдоль отрезка** движения, а не
только в конечной точке, — иначе быстрый пролёт проскакивал рок между тиками.

**Корабль не застревает в камне.** Отказ от всего шага целиком и был причиной: прижавшись к камню,
корабль выбрасывал вместе с движением внутрь и ту часть, которая уводила прочь. Теперь оси
пробуются по отдельности, как у ходьбы внутри, — корпус скользит вдоль камня. Плюс пробоина раз в
1.5 секунды контакта, а не тридцать раз в секунду. Тест переписан на то, что действительно важно:
после тарана пилот **выводит корабль назад**.

**Через астероид в корабль больше не зайти.** Камень, лежащий у борта, был дырой в обшивке: обходя
его, попадаешь внутрь корпуса. Ходьба по камню теперь блокируется, если шаг заводит внутрь силуэта
корабля.

**Взгляд по мышке.** `FacingDirection` служил одновременно направлением ходьбы, так что просто
навести его на курсор было нельзя — персонаж пошёл бы к курсору. Добавлено отдельное
`LookDirection` (протокол: `LookX/LookY`): им светит фонарь скафандра, ноги идут своим курсом. На
консолях (штурвал, турель, открытая панель) не шлётся — там мышь принадлежит консоли.

**Текстура камня.** Тот же многоугольник, залитый веером треугольников, с фасеточным затенением от
источника слева-сверху, россыпью щебня, кратерами с подсвеченным краем и контровым светом по
солнечной кромке. Треугольников в этом пайплайне нет, поэтому заливка — развёртка тонких квадов из
центра, тем же приёмом, что рисуются линии в панели проводки.

**Проверено**: 173/173 (2 новых на геометрию: контур камня стабилен и не круг; провал между пилонами
корвета — открытый космос, а не палуба). Картинку астероидов вживую снять не удалось — скриптовый
пролёт до пояса не доехал, а захват экрана в этой сессии стабильно ловит чужое окно.

## Штурвал: WASD вместо джойстика

Мышиный джойстик задавал вектор тяги **в мировых координатах**, а курс корабль выбирал сам —
доворачивался туда, куда его несёт. То есть пилот управлял траекторией и не управлял тем, куда
смотрит нос. Для корпуса, у которого пушки на бортах, а шлюз на конкретной стене, нос — это как раз
то, чем рулят.

Теперь: **W** — ход по носу, **X** — назад (45% тяги: маневровые, чтобы отойти от причала или
выползти из камня, а не летать), **A/D** — поворот носа, **S** — стабилизация. Протокол:
`HelmThrustX/Y` → `HelmThrottle`/`HelmTurn`. `_shipRotationDegrees` больше не выводится из скорости,
а интегрируется из ввода; тяга прикладывается вдоль носа (`ShipNoseDirection`, с учётом
`Ship.ForwardDegrees`). Поворот **не** снимает стабилизацию — тормозить и одновременно доворачивать
корпус нормальное желание, — а вот тяга снимает.

`EnterStationApproach` теперь ставит нос **на станцию** (`-Ship.ForwardDegrees`), а не жёстко в +X:
подлёт начинается без разворота на любом корпусе.

Круг штурвала остался, но стал прибором: линия носа с блоком-«носом» по ободу и полоса тяги от
центра (золотая вперёд, бирюзовая назад). Тянуть его больше нельзя — руки на клавишах.

**Ловушка в тестах**: полёты «в мировом направлении» больше не выражаются одной командой. Добавлен
`SteerToward` — доворачивает нос на цель и даёт газ только когда доворот меньше 25°, иначе корабль
уходит по дуге мимо. На нём теперь подлёт к причалу и таран астероида; «выехать назад из камня» стало
просто `HelmThrottle: -1`.

**Проверено**: 174/174 (новый тест: поворот двигает нос и не двигает корабль, ход идёт строго по
носу, реверс уводит против носа без разворота) плюс живой запуск: пульт с новым прибором и
подсказкой, кнопка стабилизации горит и держится.

## Магниты — касание, а не притяжение; и настоящая порода

**Захват срабатывал слишком рано.** Ботинки хватали за 2 единицы от корпуса и за 1.5 от камня
(`ShipAttachZoneMargin`/`AsteroidAttachZoneMargin`), после чего `SnapToHullSurface` подтягивал
персонажа вплотную. Со стороны это выглядело так, будто прыжок обрывают на полпути: суит ещё летит,
а его уже приклеили к поверхности, до которой он не долетел. Обе зоны теперь **0.5** — чуть больше,
чем `HullWalkClearance` (0.35), на которой персонаж стоит. Тоннелирования это не создаёт: шаг всё
равно проверяется целиком (`TryAutoAttachAlong` сэмплит отрезок через 0.25), а не только его конец.

**Толчок ослаблен**: `PushOffSpeed` 4 → **2.4**. Это отталкивание от поручня, а не прыжок; промах
теперь видно в полёте и его успеваешь исправить ранцем.

**Ловушка в тестах**: старые хелперы прекращали полёт «достаточно близко» (1 единица) и полагались
на то, что магниты добьют остаток. Теперь `ExitShipAndFlyTo`/`ReturnAboardFromEva` летят до
фактического захвата (`IsEvaAttached`) — иначе персонаж оставался дрейфовать рядом с камнем, а
дрейфующему с пустым ранцем не от чего оттолкнуться, и обратная дорога не начиналась вовсе.

### Астероиды: запечённая поверхность вместо набора квадов

Камень рисовался десятком затенённых квадов поверх полигона — этим можно сказать только «тут
светлее, там темнее». Теперь на каждый астероид один раз печётся текстура (`AsteroidTexture`):
поле высот, освещённое по нормалям на каждый тексель, с кратерами, трещинами, ржавыми и базальтовыми
зонами и выветренной коркой по краю. Маска — та же `AsteroidShape.RadiusAt`, что и у физики, так что
картинка и столкновение остаются одной формой.

Что важно в реализации:

- **Рельеф** — billow-шум (складка даёт узловатые комья, а не гладкие дюны) + ridged-слой на крагах
  + мелкое зерно; трещины — только гребень ridged-поля в 10-й степени, иначе получаются широкие
  связные каналы, и камень выглядит как **пазл** (первая версия именно так и выглядела).
- **Домен поворачивается между октавами** (0.6 рад) и между слоями. Value-шум живёт на квадратной
  сетке; октавы на одних осях совпадают ромбами, и поверхность становится похожа на **ткань**.
- Свет запечён в мировых координатах, а рисуется текстура повёрнутой на тот же угол, на который
  повёрнуто поле на экране, — звезда стоит на месте, пока мир крутится вокруг всегда вертикального
  корабля. Масштаб берётся из самого преобразования (`worldToScreen` на векторе (1,0)), а не из
  константы зума.
- Печётся **не больше одного камня за кадр**; ожидающие рисуются плоской заливкой по своему контуру.
  Пять текстур разом — заметный провал кадра в момент входа в пояс, пять за пять кадров — ничего.
- Смотреть на результат можно не запуская игру: `AsteroidTexture.BakePixels` не требует
  GraphicsDevice, так что превью рендерится отдельной консольной программой в PNG.

**Проверено**: 175/175 (новый тест `World_Eva_BootsGrabOnContact_NotAcrossTheGap` меряет зазор в тик
до захвата — контакт около единицы, а не пара единиц старых магнитов) плюс отрисовка четырёх камней
в PNG.

## Реактор, астероиды на радаре и внешность корвета

**Расход топлива.** `fuelPerPowerUnitPerSecond` 0.05 → **0.006**. Полный комплект стержней при
максимальной нагрузке жил меньше трёх минут полёта — реактор превращался в рутину, которую кормишь
через прыжок. Теперь это порядка двадцати минут на полной и заметно дольше на крейсерской.
Тест `World_Voyage_StationRefuelsAndClearsBreaches` проверял «дозаправка добавила ≥10 единиц» — это
утверждение про скорость расхода, а не про дозаправку; переписан на «бак снова почти полон».

**Астероиды на карте капитана** рисуются своим настоящим контуром (`AsteroidShape.Outline`), а не
квадратом: квадратная точка говорит «здесь что-то есть», контур — проходим ли промежуток, в который
целишься. Заливка/обводка полигона вынесены в `Primitives` (`FillTriangle`/`FillPolygon`/
`StrokePolygon`) — раньше свой `DrawTriangle` лежал внутри `FieldRenderer`.

### Обшивка: корабль вместо плана этажей

Отсеки обязаны оставаться прямоугольниками — по ним раздельно по осям считается ходьба и линии
видимости. Но корпус, который из них складывается, не обязан. Новый `HullSkin` рисуется **под** всем
интерьером:

- плита на каждый отсек, отступ 0.36 и **срезанные углы**;
- **носовой купол** с фонарём кокпита у самого переднего отсека (направление берётся из
  `ShipCatalog.ForwardDegrees`, чтобы рендер не собирал `Ship` ради одного числа). Размах купола
  равен прямой части плиты — купол во всю ширину нависает над срезами и читается как шляпа;
- **кормовая перемычка** между двумя отсеками, уходящими дальше всех назад: у корвета хвост — пара
  пилонов с двигателями, и без перемычки они читаются как ноги;
- подсветка сверху-слева и тень снизу-справа на каждой плите, **бортовые огни** (красный слева,
  зелёный справа) и сенсорные блистеры по внешним бортам.

Кокпит сужен до 4.5 (был 5.5 во всю ширину хребта) — ступенька к оружейной и есть сужение носа.

### Интерьер: `RoomDecor`

Цвет отсека по назначению (по id, а не таблицей на класс корабля), крашеная дорожка вдоль длинной
оси, табличка с названием на цветной подложке, световое пятно от потолочного плафона, лампы на
стенах и **скруглённые внутренние углы** — заливка сектора между углом и дугой. Прямоугольник
остаётся прямоугольником для всего, что считает; глаз видит скруглённую переборку.

**Проверено**: 175/175 и живые скриншоты — вид из перископа (весь корпус целиком) и реакторный
отсек изнутри.

### Железо на корпусе (`HullSkin.Fittings.cs`)

Обшивка была гладкой — корпус читался как геометрия, а не как корабль. Добавлено то, что на
настоящем судне торчит наружу:

- **сопла** на корме каждого отсека с двигателем: раструб, тёмное жерло с подсвеченной губой и пара
  подкосов. Факел рисует `FieldRenderer` и только на ходу — раструб есть всегда, иначе корабль на
  приколе выглядит как здание;
- **радиаторные рёбра** по внешним бортам, в корму от середины;
- **стыковочные воротники** вокруг каждого внешнего шлюза, с жёлтыми захватами — выход наружу видно
  и снаружи, а не только из коридора;
- **окраска по хребту**: тёмная полоса с двумя янтарными линиями, от основания носа до кормы;
- **палубные детали** в виде люков с заклёпками и лёгкий разброс тона плиты по id отсека.

**Ловушка**: полоса окраски сначала вышла чёрным провалом во всю длину корабля. `Primitives`
заливает полигон веером полос от центра, полосы перекрываются — для непрозрачного цвета это
незаметно, а полупрозрачный складывается сам с собой в несколько слоёв. Краска рисуется одним
повёрнутым квадом.

**Проверено**: 175/175 и живые скриншоты — корпус целиком из перископа и реакторный отсек изнутри.

## Абордаж: три класса вражеских корпусов и воздух внутри них

Из плана (`game_design.md` §12) взята связка «разные планировки вражеских кораблей + атмосфера на
них». Это было самое слабое место готового: абордаж каждый раз проходил по одному и тому же
коридору, и вражеский корабль был единственным местом в игре, где воздух не моделировался вообще —
то есть перестрелка без риска задохнуться.

### Классы корпусов

`EnemyShipClass` + `EnemyShipLayout.Classes.cs` — три плана, ровно тем же приёмом, каким станции
получили `StationKind`:

- **Рейдер** — прежние три отсека в линию, три человека. Обычная оппозиция.
- **Грузовик** — длинный трюм с кубриком, четверо, из них боец один, скафандров нет ни на ком.
- **Канонерка** — орудийная палуба, машинное, мостик; экипаж в скафандрах, кроме механика.

Ключевое: **id уникальны по классам** (`raider-`/`freighter-`/`gunship-`). Состояние дверей и
комната, в которой стоит персонаж, — плоские словари, общие на все структуры игры; два класса с
комнатой `bridge` были бы одной и той же комнатой. Двери всех классов регистрируются в конструкторе
`World`, как это уже сделано для всех видов станций.

Какой корпус защищает сектор — детерминированно от id сектора (`EnemyClassFor`, свой FNV-хеш, потому
что `string.GetHashCode` рандомизирован по процессу). Сбежать из боя и вернуться — та же оппозиция,
иначе отступление было бы способом переролить канонерку в грузовик. Ведущий корабль эскадры никогда
не грузовик.

`EnemyShipRuntime` носит свой `Layout`; `World.EnemyShipLayout` — это план **того корабля, который
сейчас можно взять на абордаж**. Уже существовавший механизм `_crewShipId` в `ResolveEnemyLosses`
пересобирает экипаж при смене корпуса — туда же добавлено выбрасывание абордажной команды наружу:
их `RoomId` называет отсек структуры, которой больше нет.

### Воздух (`World.EnemyAtmosphere.cs`)

Модель корабля игрока минус всё, чего у врага нет (генератор, завариваемые пробоины):

- отсек за пробоиной — вакуум и остаётся им;
- **внутренние двери закрыты** по умолчанию: экипаж, которого берут на абордаж, задраивается;
- открыть дверь — значит стравить воздух из отсека за ней;
- без скафандра в разгерметизированном отсеке — тот же урон, что и на своём корабле;
- задохнувшийся последний защитник отдаёт корпус так же, как застреленный.

Отсюда два способа взять корабль: зачищать отсек за отсеком или открыть двери и подождать. Работает
второй или нет — решает, носит ли экипаж скафандры, и это то, чем грузовик отличается от канонерки.

**Грабли, которые всплыли:**

1. Защитник в пробитом отсеке обязан быть в скафандре — иначе он умирает от вакуума ещё до прихода
   абордажной команды, и входной бой достаётся даром.
2. `StepEnemyAtmosphere` падал с `KeyNotFoundException` в тик между гибелью корпуса и пересборкой
   экипажа: словарь кислорода держал комнаты старого класса, а план уже был новый. Атмосфера теперь
   помнит, чьи это комнаты (`_enemyAtmosphereKind`), и пересобирается при смене.
3. `ResetEnemyCrew` при пустом небе создавал экипаж запасного плана — трёх защитников, стоящих в
   пустоте. Теперь нет корабля — нет экипажа.

**Проверено**: 179/179, из них 4 новых (уникальность структур всех классов; сектор всегда выставляет
тот же корпус; закрытый корпус держит воздух, открытые двери его стравливают и убивают тех, кто без
скафандра, не трогая тех, кто в скафандре; потеря корпуса выбрасывает абордажную команду наружу)
плюс запуск клиента.

## Кислородный баллон, резак-луч, руда блоками и видимые пули

Четыре связанные правки по прямому запросу.

**Личное оружие стреляет снарядами** (`World.PersonalShots.cs`). Было: нажал пробел — ближайший в
комнате потерял здоровье, промахнуться нельзя. Стало: пуля выходит из персонажа по направлению
курсора, летит со своей скоростью и попадает в то, что реально оказалось на пути. Стена по-прежнему
останавливает — снаряд умирает на границе отсека, в котором выпущен; старая проверка «та же комната»
теперь выражена физикой, а не фильтром. Экипаж отстреливается такими же видимыми снарядами.

**Кислородный баллон** (`OxygenTankDefinitions`, `World.OxygenTanks.cs`) — первый предмет, который
вставляется в другой предмет. Гнездо есть у скафандра и резака; под слотом в инвентаре рисуется
ячейка с остатком. Взять баллон в руку и кликнуть по ячейке — вставить, клик по полной — вынуть.
Резак без баллона не зажигается, скафандр без баллона не пускает в шлюз и не спасает от вакуума.

Слот инвентаря хранит **тип**, а не предмет, поэтому заряд лежит рядом со слотом
(`Inventory.MainSlotTanks`, `WornSuitSlot = -1` для надетого скафандра), и переносится вместе с
вещью. На полку с типами предмет с баллоном не кладётся, пока баллон не вынут — иначе он бы молча
пропал.

**Расход**: баллон тратится, только когда скафандр реально в вакууме — снаружи или на чужом
разгерметизированном корпусе. Внутри своего корабля не тратится, и это осознанная граница: честная
симуляция (тратить и в своих пробитых отсеках) наказывала за правильную игру — экипаж, который
оделся как надо, тихо задыхался в середине долгого боя. Стыковка пополняет все баллоны, как чинит
корпус и заправляет реактор.

**Руда — блоки, а не значок со счётчиком.** 2–3 блока на астероид, у каждого ХП и полоска; спиленный
роняет один предмет. Резак работает **на ЛКМ**, как в Barotrauma: короткое синее пламя из персонажа
в сторону курсора, пламя задевает блок — блок пилится.

**Грабли:**

1. Стойка с баллонами в метре от шкафа со скафандрами: `HandleInteract` проверяет стойки раньше
   шкафа, и «взять баллон» превращалось в «снять скафандр». Радиус взаимодействия 1.0 — всё, что
   рядом, должно стоять дальше.
2. Тесты флакали (177–180 из 181 без изменений кода): `Random` в `World.EnemyAi.cs` заводился от
   часов. Теперь сеется от счётчика — прогон воспроизводим, но два World подряд всё ещё катят
   по-разному, на что опираются тесты, повторяющие сценарий до попадания.
3. `MoveCharacterTo` ведёт по обеим осям сразу: выход из шлюзовой камеры по диагонали покидает полосу
   двери раньше, чем доходит до стены, и перехода не происходит. Сначала выйти на высоту двери.

**Проверено**: 181/181.

### Правки после игры: размер персонажа, взгляд снаружи, резак внутри

- **Персонаж снаружи был 10 px, внутри — 34** (0.7 юнита). Стоило выйти в шлюз, и человек уменьшался
  втрое. Снаружи теперь тот же размер, что внутри: пространство одно и непрерывное, значит и масштаб
  один.
- **Белая точка взгляда снаружи смотрела не туда.** Снаружи `Facing` хранится в координатах поля, а
  сцена рисуется в системе корабля, которая крутится вместе с корпусом. Теперь направление
  сворачивается через `ShipLocalFrame.ToLocalDirection` — как и всё остальное в этой сцене. То же
  касается пламени резака.
- **Резак горит везде** — внутри корабля, на станции, на захваченном корпусе; тратит баллон.
  Пилить по-прежнему нечего нигде, кроме поля с астероидами: руда существует только там.

## Кооп по сети: один корабль, несколько игроков

Мультиплеер оказался не переделкой игры, а новой реализацией двух интерфейсов. Симуляция уже была
серверной и уже была рассчитана на нескольких игроков: `World` держит `Dictionary<int, Character>`,
весь ввод (`_moveInput`, `_cutInput`, `_weaponCooldowns`, `_stolenItemCount`) уже был per-playerId,
клиент везде фильтрует по `_client.PlayerId`, а рисует **всех** персонажей из снапшота. Работа свелась
к транспорту, лобби и тому, что вылезает только при втором игроке.

**Формат кадра** (`Shared/Networking/Wire.cs`): `[4 байта длины][1 байт флагов][UTF-8 JSON]`, deflate
при размере от 1 КБ. JSON, а не бинарь: `WorldSnapshot`/`ClientCommand` меняются каждую фичу, а формат,
читающий по именам, не требует правок в такт. Цена — размер, и его гасит сжатие: полный снапшот
28.8 КБ превращается в **7.4 КБ** на кадр (тест `Wire_SnapshotFrameStaysWithinBudget` держит потолок
24 КБ), то есть ~1.8 Мбит/с на игрока при 30 тиках. Снапшот по-прежнему шлёт всю статику (комнаты,
станцию, точки галактики) каждый тик — в процессе это была передача ссылки, по сети это повторяющийся
текст, который deflate схлопывает почти в ноль. Делить снапшот на «статика один раз + динамика»
понадобится, только если бюджет перестанет сходиться.

**Транспорт** (`TcpServerConnection`/`TcpClientConnection`): TCP c `NoDelay`, по потоку на каждое
направление, чтобы ни чтение, ни запись не могли затормозить тик. Асимметрия по назначению:
снапшоты хранятся в слоте «только последний» (отставший клиент должен увидеть настоящее, а не
проигрывать очередь устаревших миров), команды — в очереди без потерь (в команде едет edge-triggered
событие: клик по двери, выстрел, покупка — потеряешь кадр, и события просто не случится).

**Рукопожатие**: `IServerConnection.Send` умеет только `WorldSnapshot`, а свой `playerId` клиент
раньше узнавал из возврата `GameServer.Connect` — по сети возвращать некуда. Поэтому конверт
`ServerMessage = Welcome(playerId) | Snapshot`, и первый кадр в сокете всегда `Welcome`.

**Listen-сервер**: `NetworkHost` — слушающий сокет поверх уже работающего `GameServer`. Хост остаётся
обычным игроком на `InProcessTransport`, соло-путь не изменился ни на строчку; `SoloSession` получила
необязательный `listenPort`. В меню: `[H]` открывает кооп (порт 47624, тут же показываются локальные
адреса, которые диктовать друзьям), `[J]` — экран подключения с вводом адреса. Само подключение идёт
в `Task`, иначе окно замирало бы на весь таймаут.

**Что чинилось из-за второго игрока:**

1. `GameServer.Connect` добавлял в `List`, по которому в это же время шёл тик с другого потока. Теперь
   id выдаётся сразу (он нужен для `Welcome`), а персонаж спавнится в начале следующего тика.
2. Отключения не существовало вообще. `IServerConnection.IsOpen` (default-реализация — «всегда
   открыт», соло об этом не думает), `World.RemoveCharacter` убирает персонажа, его ввод, кулдауны,
   счётчик краж и **освобождает турель**: иначе орудие остаётся занято игроком, которого нет.
3. `ApplyCommand` падал на `_characters[playerId]`, если команда пережила отправителя на тик.

**Осталось не сделанным** (осознанно): сохранение хранит инвентарь только первого игрока
(`World.Save.cs`), правил смерти/респавна для экипажа нет, интерполяции чужих персонажей нет — на
30 Гц по локальной сети она не нужна, по интернету может понадобиться.

**Проверено**: 187/187, плюс живая проверка двумя окнами — хост открывает кооп и начинает игру, второй
клиент подключается по 127.0.0.1, оба видят друг друга, движение гостя видно у хоста в реальном времени.

## Боты экипажа: наём и автономная работа по роли

game_design.md section 10 explicitly deferred this ("Кадровик... пока не делаем"); implemented now
on request. New `NpcKind.Recruiter` staffs every station kind (Outpost/Trade/Shipyard -
`Station.Default.cs`); its dialogue panel lists 3 randomly rolled `BotCandidate`s (name, `CrewRole`,
cost scaling with a random 100/150/200% quality tier), rerolled on every docking the same way the
Trader's stock refreshes.

**A hired bot is an ordinary `Character`**, keyed by a negative id (`--_nextBotId`, never collides
with `GameServer`'s incrementing positive ids) and marked `IsBot`/`BotName`/`Role`
(`World.Recruiting.cs`). It never receives a `ClientCommand` - `GameServer` doesn't know it exists -
and never moves: no pathfinding exists anywhere in this codebase (`World.EnemyAi.cs`'s "AI" is dice
rolls), so a bot is placed once, permanently, at its role's real fixture (helm/distribution
block/reactor/a turret's periscope) and never walks. Standing at the post it does its job at all
game is indistinguishable from having walked there.

**`World.CrewAi.cs`'s `StepCrewBots`** runs each role every tick:
- **Security** claims a free turret and keeps it forever; aims by folding the boardable enemy's
  field position into the turret mount's own unrotated frame (the exact inverse of the geometry
  `TryFire` already uses to send a shot out of it) and fires once aligned.
- **Engineer** nudges the single shared power-allocation slot (`PowerGrid.ApplyInput`) toward
  Oxygen/Shields/Engine/WeaponCharger in that priority order - only actually contends with a live
  player's own input in the same tick, which is rare and self-resolving next tick.
- **Mechanic** reloads any empty reactor rod slot and clears one broken thing ship-wide (a jammed
  turret or a cut wire) on a 4-second cooldown - ship-wide rather than proximity-gated, since there's
  nothing for it to walk to.
- **Medic** continuously heals whoever's worst off, ship-wide - no consumable to run out of, since
  it's a standing job, not an item.
- **Captain** is a safety net, not a pilot: engages auto-stabilize if the ship is coasting and no
  live player is at the helm.

Cap of 4 hired bots (`World.MaxHiredBots`). Client: `StationPanel`'s Recruiter view lists the board
and current headcount; `ShipRenderer.DrawCharacter` draws a bot in steel blue with its name+role
label instead of the ordinary crew orange.

**Grabbing a test-only wall this ran into**: reaching the 4-bot cap costs more than the 300 credits
a fresh game starts with - a real limitation of the hiring economy, working as intended, but it meant
the cap test couldn't just spend its way there. Tests fund themselves through the save/load path
(`SaveGame.Credits` + `World.ApplySave`) instead of grinding bounty quests for real, which would have
tangled unrelated tests up in the faction-standing system for no reason. Also found along the way:
a "re-dock and check the roster rerolled" helper that only sent `TravelToPointId` and stepped never
actually re-docked at all - arriving at a station now only drops the ship into `StationApproach`
(manual docking, an earlier session's own work) and idles there forever without a helm hand actually
flying it in, silently making every "reroll" a no-op. Fixed by reusing the existing `DockAtStation`
test helper instead of reimplementing the trip.

**Проверено**: 198/198 (11 new tests: roster generation, hire/credit/cap gates, and one live-behavior
test per role - a Security bot actually lowering enemy HP through its own aim+fire loop, a Mechanic
reloading a drained rod, an Engineer raising Oxygen allocation from zero, a Captain braking a coasting
ship, a Medic's no-op-on-healthy-crew contract).

## Полная система проводов и функциональных блоков (M19-M23): замена M14

По явной просьбе — полноценный редактор схем в духе Barotrauma вместо прежней фиксированной
проводки. Заменяет `WireNetwork`/`WireLink`/`WireNode` (Shared/Model) и `WireLinkState` (Protocol)
целиком; удалена клиентская `WiringPanel` и терминал `WiringTerminal` на всех 4 корпусах.

**Модель (Shared/Model, Shared/Protocol)**: `ComponentKind` — 3 встроенных вида корпуса
(`Distribution/Junction/Device`) + 14 покупаемых (вентили И/ИЛИ/НЕ/Искл.ИЛИ, `Timer`, `Memory`,
`Relay`, 4 датчика, 3 исполнителя). `PinKind` различает Power и Signal — они никогда не
соединяются друг с другом. `Component`/`Wire`/`PinRef` заменяют `WireNode`/`WireLink` — `Wire`
хранит только два конца (`PinRef`), без физического пути (путь при прокладке — чисто визуальный
момент, для связности/ремонта/логики нужны только конечные точки). `WireGraphFactory` строит
встроенную разводку корпуса **из реальных данных корпуса** (`Ship.SystemDevices`), а не из
отдельного жёстко прописанного списка, как раньше — попутно снимает старое требование "каждый
корпус обязан иметь одинаковый набор из 7 устройств".

**Ключевое правило (Wire.cs)**: выходной пин — неограниченный веер; Power-вход берёт до 2 проводов
(это и есть обобщённый механизм резерва — "хотя бы один из двух проводов жив" воспроизводит старое
`HasBackup` для каждого силового входа бесплатно); Signal-вход — ровно 1 (правило слияния для >1
источника — неочевидный игроку эффект, которого проект сознательно избегает).

**Сервер, `World.Wiring.cs`**: `GetEffectivePower`/`IsDeviceConnected` — рекурсивный обход
связности по графу вместо жёсткой проверки "магистраль+отвод". Пойманный по пути баг: рекурсия
неверно трактовала выходной пин распределительной коробки (Junction) — обращалась к проводам,
СЛУШАЮЩИМ этот пин, которых нет (коробка сама источник для своих отводов, а не приёмник) — из-за
этого ломалось вообще всё питание корабля, не только проводка. Исправлено спецкейсом: выход
коробки всегда равен её единственному входу.

**Сервер, `World.ComponentLogic.cs` (M21-M22)**: `StepComponentLogic` считает Signal-граф
ограниченным числом проходов релаксации (`MaxPropagationPasses=8`), НЕ топологической сортировкой —
игрок может и будет разводить схемы с обратной связью (например, память, заведённая через НЕ сама
на себя — рабочая "мигалка", а не баг); каждый тик стартует от значений прошлого тика, так что
устоявшаяся схема остаётся устойчивой, а зациклённая просто колеблется, не вешая симуляцию. Таймер —
задержка включения (копит `_timerHeldSeconds`, сбрасывается мгновенно при падении входа). Память —
SR-защёлка, при одновременном set+reset побеждает reset. Датчики читают **свою же комнату**
(`Component.RoomId`) — отдельной настройки "что слушать" не нужно; `PowerLossSensor` — исключение,
следит за реактором в целом, не за конкретной системой (упрощение первой версии). Исполнитель двери
форсирует её **открытой** при true и просто отдаёт управление обратно при false — форсировать
закрытие было бы плохим эффектом, если в проёме стоит игрок.

**Сервер, физическая прокладка (M20, `World.Wiring.cs`'s `HandlePinInteract`)**: игрок кликает пин,
держа `WireSpool` (с проверкой дистанции на сервере — в отличие от старого доверительного клика по
панели); второй клик по тому же пину — отмена; по другому совместимому и не переполненному входу —
провод создан, катушка потрачена; по несовместимому — прокладка перезапускается от нового пина
(не тупик). `Character.LayingWireFromPin`/`CharacterState` — видно другим игрокам в кооперативе.

**Сервер, экономика (M23, `World.ComponentMounts.cs`)**: 14 новых `ItemType` 1:1 с `ComponentKind`
(имя/метка берутся из `ComponentDefinitions`, не дублируются в `ItemDefinitions`). Три
взаимоисключающих правила на одном гнезде `ComponentMount`: гаечный ключ/отвёртка у занятого гнезда
снимает деталь и обрывает её провода; подходящий предмет в руке у пустого гнезда — устанавливает;
пустые руки у занятого гнезда с реле — переключают его как кнопку. Держим `WireSpool` — гнездо не
реагирует вообще (не путать с прокладкой). Покупка нового корпуса сбрасывает всю разводку и
установленные блоки к заводским (`InitializeShipState` → `InitializeWiring`/`InitializeComponentMounts`).

**Пойманный по пути баг теста (не в проводке)**: `World_Recruiting_EngineerBotFeedsUnpoweredSystems`
стал падать детерминированно (не флейково) из-за сдвига RNG-сида статическим счётчиком при
добавлении новых тестов раньше по списку. Причина: `RerollUntilRoleOffered`'s поездка в бой и
обратно оставляла Engine держащим весь бюджет реактора (60 из 60), и Engineer-бот никогда не
СНИЖАЕТ уже забитую систему (только поднимает то, что ниже цели) — тупик, из которого бот сам
никогда не выйдет. Исправлено: тест явно сажает Engine до найма бота (пока никто не оспаривает
общий слайдер питания), а не полагается на то, что реролл его не заполнит.

**Клиент**: реализован отдельным проходом после серверной части. `ComponentRenderer.cs` (новый) рисует
пустые гнёзда контуром, занятые — панелью+заклёпками в цвете категории с 2-4-буквенной меткой
(`ComponentDefinitions.ShortLabel`), пины — мелкими квадратами по сторонам (вход слева/выход справа
по `PinKind`), провода — линиями (зелёный = запитан/сигнал true, серый = нет, красный =
`WireState.Damaged`), провод в процессе прокладки — линия-поводок до позиции того персонажа, кто его
ведёт (свой и чужие в кооперативе). `ShipRenderer.DrawPanel/DrawRivets/DrawRectOutline` стали
`internal static` с явным `pixel`-параметром, чтобы новый файл переиспользовал тот же стиль.

`Game1.HandleMouseClick` получил новую ветку: пин реагирует только пока в руке `WireSpool` (иначе
клик по нему ничего не значит), тело гнезда — только когда катушки в руке НЕТ (чтобы клик посреди
прокладки провода не попал по гнезду); оба edge-triggered через `_pending...`-поля, как остальные
подобные действия. `ComputeHint` перестал быть статическим (нужен `_designMouse`+камера) и получил
приоритетную ветку `WiringHint` сразу после проверки `SuitActionRemaining`: отмена/завершение
прокладки под курсором, "ведём провод от X" пока никуда не наведено, "начать провод" над пином с
катушкой в руке, "установить/снять/нажать реле" над гнездом — с той же логикой edge-кейсов (гнездо
не реагирует с катушкой в руке, "снять" требует гаечный ключ/отвёртку), что и сам клик-хендлер, чтобы
подсказка никогда не обещала действие, которое клик потом проигнорирует.

`StationPanel` — 14 новых `TradeGood` не влезали в старый единственный "Купить"-столбец (упёрлись бы
в высоту панели), поэтому `GetGoodRect` теперь раскладывает индекс `TradeCatalog.Goods` по двум
столбцам: первые 10 (обычное снаряжение) — как раньше, начиная с 11-го — в третий столбец
"Компоненты" правее "Продать". Клик-хендлер не менялся — он и так перебирает весь `Goods.Count` и
делегирует прямоугольник `GetGoodRect`.

**Проверено**: 224/224 тестов (дважды подряд без флейка — клиентские правки не трогают покрытый
тестами код), чистая сборка всего решения (`SpaceAdventure.sln`) без ошибок. Живая проверка в
MonoGame-окне не проводилась (ограничение песочницы, см. раздел про верификацию выше) — по запросу
пользователя после этого прохода.

## Фракции: видимость, новый игрок, больше последствий, война (M25-M29)

Закрывает пункт Phase 4 "полноценная динамика фракций" (`game_design.md` §12) — до этого репутация
была одним числом на фракцию, которое двигали только сдача задания и уничтожение корабля, а влияло
только на цены и доступность заданий. Пользователь выбрал все пять направлений сразу: видимость в
UI, новая фракция, больше способов менять репутацию, больше последствий в мире, война фракций.

**M25 — панель отношений (клиент, без протокола)**: `WorldSnapshot.FactionStandings` уже долетал до
клиента, но нигде не рисовался. `GalaxyMapPanel.Draw` получил список "Фракция: статус (число)" в
углу навигационной консоли и цветную рамку по фракции-владельцу вокруг каждой точки карты (`FactionColor`,
по `point.Faction`) — раньше точка красилась только по `GalaxyPointKind` (станция/сектор).

**M26 — Гильдия старателей (`FactionId.MinersGuild`) + `StationKind.Mining`**: третья фракция,
`Rival = null` как у Independent, но, в отличие от неё, её репутация двигается по общим правилам
(не освобождена особым случаем в `PriceMultiplier`). Новый вид станции добавлен тем же табличным
механизмом, что и `Trade`/`Shipyard` (`Station.Default.cs`'s `ServicesFor`) — просто ещё один case,
никакой новой инфраструктуры. Её Трейдер платит за руду на 20% больше листовой цены
(`World.Trade.cs`'s `MiningStationOreSellBonus`, `DockedStationKind`) — единственное, что реально
отличает станцию, вместо выдуманного нового NPC.

**M27 — два новых рычага репутации**: (1) `ClientCommand.AbandonQuestPressed` — отказ от задания без
докового гейта (`World.Quests.cs`'s `TryAbandonQuest`), штраф меньше, чем убийство охранника/арест
(`FactionDefinitions.StandingPenaltyForAbandoningQuest = -10`). Кнопка в `StationPanel` — тот же
`GetAdminActionRect`, что и "Сдать задание", просто в ветке "сдать здесь нельзя". (2) Сдача ЛЮБОГО
задания слегка портит отношения с соперником фракции-заказчика (`RivalStandingPerQuestTurnIn = -4`,
та же асимметрия, что уже есть у `RecordShipDestroyed`, только меньше и в обратную сторону — работать
на одну сторону само по себе маленький политический жест). Изначально в плане была "пощада вместо
добивания отступающего врага" — отброшено при реализации: выйти из `VoyagePhase.Battle`, пока хоть
один корабль жив (пусть даже отступающий), нельзя в принципе (`TryStartTravel` игнорирует смену
курса в бою), так что "оставить его в живых и уйти" физически недостижимо игроком без отдельной
переделки правил боя — не в этом плане.

**M28 — два новых мировых следствия**: (1) `FactionDefinitions.WarThreshold = -70` (строже
`HostileThreshold = -40`) — `World.StationDocking.cs`'s `CanDockNow` отказывает в стыковке вообще,
а не только в товарах/заданиях; подойти вплотную по-прежнему можно, кнопка просто никогда не
загорается. (2) `World.Factions.cs`'s `SquadronSizeAdjustment` — та же репутация, что двигает цены,
двигает и размер эскадры на входе в сектор (`World.Voyage.cs`'s `Arrive`): враждебная фракция
добавляет корабль, дружественная убирает (не ниже 1).

**M29 — война фракций (один спорный форпост)**: `_pointOwner`/`OwnerOf` в `World.Factions.cs` —
рантайм-словарь владения поверх статичного `GalaxyPoint.Faction`, тем же приёмом, каким
`_factionStanding` уже живёт рядом со статичным `FactionDefinitions`. Каждое уничтожение корабля
(`RecordShipDestroyed`, уже вызывается на каждом килле) заодно двигает `_warEffort[(проигравший,
соперник)]`; при достижении `WarEffortToFlipSector` спорная станция (`outpost-gamma`, единственная
в этой версии) меняет владельца, счётчик обнуляется. Видимость смены — не новое поле протокола:
`CreateGalaxyPoints()` отдаёт снапшоту точки с `Faction`, подставленным из `OwnerOf`, так что
клиент (который просто читает `GalaxyPoint.Faction`, как и всегда) ничего не должен знать про войну
вообще. Все места, где раньше читали `GalaxyMap.GetPoint(id).Faction` напрямую (`DockedFaction`,
`TryAbandonQuest`, `CanDockNow`, `Arrive`'s `_battleFaction`/`SquadronSizeAdjustment`), переведены на
`OwnerOf`, иначе цены/квесты/бой на "отвоёванной" станции продолжали бы молча считать её прежней.

**Пойманное при реализации взаимодействие M28×M29**: `WarEffortToFlipSector` изначально стоял на 3
("примерно 3 убийства") — ровно столько же, сколько уже стабильно набирает
`GrindStandingHostile`-гринд до `HostileThreshold` в старых тестах на `outpost-gamma`/`trade-station`.
Гринд до более глубокого `WarThreshold` вдобавок сам себя разгоняет: как только эскадра увеличивается
(M28), один визит может убить на корабль больше, а значит один "заход" способен просадить репутацию
сразу на 70+ пунктов — что попутно перескакивает и порог войны. В одном прогоне это увело
`outpost-gamma` к Вольному флоту посреди совсем другого теста (`World_Docking_AtWar_...`), который
проверял отказ в стыковке именно у Консорциума — станция сменила хозяина, и новый хозяин был не в
состоянии войны с игроком, тест ловил "стыковка разрешена" там, где ждал отказа. Исправлено на двух
уровнях: `WarEffortToFlipSector` поднят до 5 (заведомо больше, чем стоят оба обычных гринда — 3 и 4
убийства), и тест на отказ в стыковке при войне переведён с `outpost-gamma` (единственная спорная
точка) на `trade-station` (тот же Консорциум, но никогда не участвует в войне) — так проверка не
зависит от того, насколько именно гринд перелетел через порог.

**Проверено**: 239/239 тестов, три прогона подряд без флейка. Чистая сборка всего решения. Клиент
запущен и закрыт без исключений (полная визуальная проверка панели фракций и цвета отвоёванной
станции в MonoGame-окне не проводилась — то же ограничение песочницы, что и в предыдущих разделах).

## Двухуровневая карта: звёздные системы, реальный перелёт в поле, варп (M31-M33)

По прямой просьбе — переработка навигации в два слоя: между звёздными системами (варп-прыжок
почти мгновенный, но только с физического края системы) и внутри системы (капитан выбирает точку
интереса, корабль летит туда в реальном поле, просто ускоренно). M32 и M33 в итоге слиты в один
проход: варп-кнопка обязана загораться по физическому приближению в поле (как `CanDockNow`), а
это и есть ровно то, что M33 должно было построить — реальный полёт вместо абстрактной карты
(`StepTraveling` на `MapTravelSpeedPerSecond`). Строить варп поверх старой абстрактной карты, а
потом сразу её выбрасывать, смысла не было.

**M31 — модель систем, без изменения поведения**: `GalaxyPoint` получил `SystemId`; новый
`StarSystem` (свои точки + свой `AsteroidField`); `GalaxyMap` группирует точки в системы, но
плоские `Points`/`GetPoint(id)` работают как раньше (id глобально уникальны, не составной ключ) —
почти весь существующий код (`OwnerOf`, квесты, сохранения) не заметил разницы. Галактика с
самого начала — две системы («Sol» со всем сегодняшним контентом, «Альфа Центавра» заглушкой).
`World.AsteroidField` стал вычисляемым свойством от `_currentSystemId` вместо синглтона — самая
дорогая по разведке правка встала на место без единой правки в `ShipField.cs`/`Cutting.cs`/`Eva.cs`.

**M32+M33 — реальный полёт и варп**: `GalaxyPoint.X/Y` для точек внутри системы теперь — реальные
координаты поля (то же пространство, где летают астероиды), а не абстрактная карта — вторая
система координат просто исчезла. `World.Voyage.cs`'s `StepTraveling` заменён: автопилот
(`AutopilotToward`, тот же расчёт курса, что раньше жил только в тестовом `SteerToward`) через
`StepShipFieldPhysics` с `TimeCompressionFactor=8`. Ручной штурвал (`IsAtHelm`) отменяет автопилот
и ускорение на этом тике — та же логика, что уже отключает капитан-бота. Прибытие — тот же
`Arrive()`, что и всегда, просто по реальному приближению, а не абстрактному. `GalaxyPointKind.
WarpPoint` — точка у границы поля; `CanWarpNow`/`TryWarpTo` (`World.StarSystems.cs`) — тот же
паттерн, что `CanDockNow`: долетел, встал, скорость ниже порога — кнопка «Прыжок» загорается.
Система связаны все со всеми (полный граф, по выбору пользователя) — варп-цель просто любая другая
известная система. Клиент: `GalaxyMapPanel` теперь рисует точки ТЕКУЩЕЙ системы (не всех сразу —
иначе точки чужой системы легли бы на одну карту с текущей) в их реальных координатах поля, плюс
список соседних систем с кнопкой «Прыжок», активной только при `CanWarpNow`.

**Пойманные баги (в порядке обнаружения, все — взаимодействие с уже существующим кодом)**:
1. **Капитан-бот глушил автопилот.** `World.CrewAi.cs`'s `StepCaptainBot` уже дёргал
   `EngageAutoStabilize()` в фазе `Traveling`, если скорость превышала 0.5 и никто не за штурвалом
   — задумано как страховка от дрейфа, но теперь автопилот САМ и есть "никто за штурвалом", и бот
   гасил его тягу каждый тик. Исправлено исключением `Traveling` из списка фаз бота — у этой фазы
   теперь свой пилот.
2. **Ускоренный перелёт требовал мощности реактора, которой ни у кого нет на старте.**
   `IntegrateShipFieldMotion` домножает тягу на `GetEffectivePower(Engine)/ShipEngineReferencePower`
   — у свежего экипажа вся мощность на нуле, пока игрок сам не подвинет слайдер. Раньше абстрактная
   карта вообще не знала о реакторе. Добавлен `fullPower` (`IntegrateShipFieldMotion`/
   `StepShipFieldPhysics`, по умолчанию `false` — ручной полёт не изменился); автопилот включает
   его явно — это его собственный автоматический ход, а не ручной прожиг топлива.
3. **Поворот с фиксированной скоростью перелетал цель при ускорении времени.** `_helmTurn`
   бинарный (±1/0), и на несжатом тике (1/30 c) это безопасные ~3°/тик, но при 8-кратном ускорении
   — уже ~24°/тик, при пороге сходимости в 2° курс никогда не устаканивался, а качался туда-сюда
   бесконечно (наблюдалось как курс, дрожащий между двумя значениями с разницей ровно в один
   шаг/тик). Исправлено: `AutopilotToward` теперь получает тот же (возможно сжатый) `dt`, что и
   `StepShipFieldPhysics`, и если один тик поворота перекрывает оставшуюся ошибку — доворачивает
   ровно на неё, а не на полный шаг.
4. **Прямая линия от точки стыковки до половины точек карты задевала астероид.** `DockBerthPosition`
   (откуда стартует буквально любой перелёт, независимо от того, у какой станции стоял корабль) —
   фиксированная точка около центра поля, а поле астероидов занимает большую часть той же
   центральной области. Расставленные "на глаз" координаты точек задевали корпус астероида
   где-то на полпути, даже когда сама точка была далеко от любой скалы — `SlideAlongObstacle` не
   находил свободной оси, и корабль замирал намертво. Пересчитано скриптом (проверка расстояния
   от точки до ОТРЕЗКА, а не только до конечных точек, с запасом на длину корпуса) для всех 8
   точек — расстановка `GalaxyMap.cs` теперь опирается на реальную геометрию, а не на глаз.

**Проверено**: 242/242 теста, три прогона подряд. Чистая сборка всего решения. Клиент запущен и
закрыт без исключений. Живая проверка варп-прыжка и полёта к точке интереса в MonoGame-окне не

## Разбор: "сварочный баллон после космоса всё равно не работает"

Пользователь сообщил, что и ПОСЛЕ предыдущей правки (сварка в космосе) баллон "всё равно не
работает" — попросил найти настоящую причину, не гадать. Вместо дальнейших рассуждений по коду
написал реальный симулированный сценарий (сначала как временный `Scratch_...`-тест с логами в
консоль, потом как постоянный тест) и прогнал его через реальный `World`, а не рассуждал абстрактно.

Первый прогон сценария (суть до чинки: подержать сварку нажатой в открытом космосе 15 секунд без
цели в досягаемости → вернуться на корабль → пробить новую пробоину → попытаться заварить) **упал**
— пробоина не заварилась. Первая версия скрипта решила, что это подтверждает баг. Разобравшись
подробнее (напечатав позицию персонажа и координаты реально пробитого блока), оказалось: пробоина
случайно легла на ДРУГУЮ стену комнаты (нижнюю, Y=6), чем та, где стоял персонаж по скрипту (верхняя,
Y≈0.5) — расстояние ~5.5 units, далеко за пределами досягаемости горелки (1.7 units). Это не баг
игры, а баг тестового сценария: `BreachRoom` пробивает случайный блок, а верхняя/нижняя стена
равновероятны. Когда скрипт исправлен так, чтобы идти именно к тому месту, где реально появилась
пробоина, — заварка сработала штатно, баллон потратил ровно ожидаемое количество (истратил заряд на
15 секунд бесполезного держания в космосе + доли секунды на реальную сварку, и не больше).

**Реальная, подтверждённая механика (не баг, но объясняет жалобу)**: инструмент прожигает баллон,
пока зажат, ВНЕ ЗАВИСИМОСТИ от того, есть ли что заваривать в досягаемости — то же правило, что уже
у резака (жжёт кислород, даже если нет руды под рукой). Если держать ЛКМ, паря в космосе в поисках
пробоины (как и естественно пробовать при первом знакомстве с "теперь можно варить и снаружи"), за
~31 секунду баллон полностью опустошается вхолостую, без всякой обратной связи на экране — и когда
игрок наконец возвращается внутрь и пытается заварить настоящую пробоину, баллон уже пуст. Это
читается как "сварка сломалась", хотя технически всё работает как задумано (симметрично резаку).
Никакой порчи состояния при пересечении шлюза туда-обратно не подтвердилось — баллон сохраняет
именно то количество заряда, что был потрачен, ни больше, ни меньше.

Добавлен постоянный тест `World_Weld_SurvivesAnEvaRoundTripWithoutLosingUnrelatedCharge`
(`TestRunner.Eva.cs`) — держит сварку вхолостую в космосе, возвращается, находит РЕАЛЬНОЕ место
пробоины (не гадает верх/низ), заваривает её; фиксирует именно это поведение как контракт.

Не менял механику "жжёт впустую без цели" — она специально симметрична резаку, и трогать её без
явного запроса не стал; вопрос для игрока: (а) оставить как есть (реалистично: горелка жжёт газ,
даже если не касается металла), (б) не тратить баллон, пока пламя не касается пробоины (менее
"честно", но убирает эту ловушку для новичка), (в) добавить визуальный/звуковой сигнал при
опустошении баллона. Нужно решение пользователя, прежде чем менять этот баланс.

**Проверено**: `dotnet build` — чисто. 243/243 теста (242 + новый), три прогона подряд. Клиент
запущен и закрыт без исключений. Живая проверка в MonoGame-окне не проводилась.

## Настоящая причина: "сварка перестаёт работать НЕ из-за пустого баллона"

Пользователь возразил на разбор выше — воспроизвёл ситуацию вживую и показал скриншот вместо
дальнейших догадок по коду. На HUD боя (`CombatPanel.cs`) было видно: **"Здоровье: 0/100
[скафандр]"** — здоровье персонажа буквально ноль.

`World.Welding.cs`/`World.Cutting.cs` обе гейтуют первой же строкой: `character.Health <= 0` →
полный отказ, ничего не варит и не режет. А `World.Injuries.cs`'s собственный комментарий прямо
признаёт: "No named wound types... and no death/respawn handling yet" — при 0 HP персонаж НЕ
умирает и не респавнится, а просто продолжает стоять и ходить с нулём здоровья бесконечно, без
какого-либо явного игрового состояния "вы недееспособны". Единственный путь назад — аптечка
(`TryUseMedKit`, `World.Injuries.cs`) в руке.

Заодно нашёлся настоящий баг того же семейства: бот-медик (`World.CrewAi.cs`'s `StepMedicBot`)
отбирал пациента условием `c.Health < MaxHealth && c.Health > 0` — то есть ИСКЛЮЧАЛ ровно того, кому
лечение нужнее всего (тех, кто уже на нуле)! Нанятый медик никогда не поднимет упавшего до 0 HP
члена экипажа — только сам игрок аптечкой. Исправлено на `c.Health >= 0` (эквивалентно "не
исключать никого", т.к. Health и так всегда клэмпится к 0 снизу).

Добавлена подсказка на HUD (`CombatPanel.cs`): при `Health <= 0` под строкой здоровья появляется
красным "НЕДЕЕСПОСОБЕН - нужна аптечка (сварка/резак не работают)" — раньше единственным сигналом
была сама цифра "0" в мелкой строке статуса, легко не заметить, особенно среди боя.

**Проверено**: `dotnet build` (Tests-проект + Client в отдельную temp-папку, т.к. клиент был
запущен пользователем для живого репро — не трогал его исполняемый файл). 243/243 теста, два
прогона подряд. Живьём HUD-подсказку и лечение медиком с 0 HP не проверял — увидите на следующем
перезапуске клиента.
