# Space Adventure — контекст для продолжения работы

Этот файл — конспект для Claude (или любого другого агента), который продолжит работу над
проектом на другой машине/аккаунте без доступа к истории текущей сессии. Дизайн-документ
(`game_design.md`) и архитектурные заметки (`architecture.md`) остаются основным источником
истины по геймплею; этот файл — про то, что уже сделано и как с этим работать.

## Что это за проект

Кооперативная 2D top-down игра про экипаж корабля (Barotrauma / Pulsar: Lost Colony / FTL).
C# / .NET 9 / MonoGame (WindowsDX). Клиент-серверная архитектура с первого дня: соло-игра —
это клиент, который в фоновом потоке поднимает встроенный сервер и общается с ним через
in-process транспорт (`InProcessTransport`), но серверная симуляция ничего не знает про то,
что клиент "локальный" — при необходимости транспорт заменяется на реальную сеть без переписывания
модели.

## Структура решения

```
Space adventure/
  game_design.md       — дизайн-документ (источник истины по геймплею, фазы 1-4)
  architecture.md       — архитектурные заметки/открытые вопросы
  SpaceAdventure.sln
  src/
    SpaceAdventure.Shared/    — модель данных + протокол, без MonoGame-зависимостей
    SpaceAdventure.Server/    — вся симуляция (World.cs + partial-файлы по темам)
    SpaceAdventure.Client/    — рендер/ввод, никакой игровой логики
    SpaceAdventure.Tests/     — ручной test runner (без внешнего фреймворка), TestRunner.cs
```

### Сборка / тесты / запуск

```bash
dotnet build "SpaceAdventure.sln"
dotnet run --project src/SpaceAdventure.Tests --no-build     # 57/57 должно быть зелёным
dotnet run --project src/SpaceAdventure.Client --no-build    # запускает окно игры (Windows-приложение)
```

Если `dotnet build` зависает — это почти всегда NuGet-рестор для `dotnet-mgcb` (Content Pipeline)
в песочнице без сети. Решение: включить реальный доступ к сети для команды сборки (в Claude Code
это `dangerouslyDisableSandbox: true` у Bash-тула). После первого успешного восстановления пакет
кэшируется и дальше собирается офлайн без проблем.

## Конвенции проекта (важно соблюдать)

- **Файлы держим маленькими.** Как только класс разрастается на несколько обязанностей — делим
  на `partial class` по темам. Пример: `World.cs` (ядро) + `World.Movement.cs` + `World.Combat.cs`
  + `World.Interact.cs` + `World.Voyage.cs` + `World.EnemyAi.cs` + `World.Atmosphere.cs` +
  `World.Reactor.cs`.
- **Shared = только данные** (records, enums, простая геометрия/математика). **Server = вся логика**.
  **Client = только рендер и перевод ввода в команды**, никакой симуляции на клиенте.
- **Тесты** — ручной раннер: массив `(string Name, Func<bool> Run)` в `TestRunner.cs`, каждый тест
  — статический метод, возвращающий `bool`. Никакого xUnit/NUnit. При добавлении новой механики
  почти всегда нужно добавить 2-5 тестов рядом с похожими.
- **Перед крупными фичами — сначала описать план в чате и получить подтверждение**, только потом
  кодить. Пользователь несколько раз явно просил "сначала скажи, что будешь делать, не кодь".
- После любых серьёзных изменений: `dotnet build` → `dotnet run` тестов → если есть визуальный
  эффект, ещё и живой запуск клиента с скриншотом (см. раздел про верификацию ниже).

## Явные решения по скоупу (не предлагать снова без явной просьбы)

- **Боты для ролей экипажа (инженер/механик/охрана/капитан) осознанно отложены.** Пользователь
  прямо сказал не делать их, пока не попросит явно. Сейчас вся игра — один игрок, который должен
  разрываться между ролями (это принято как есть).
- Реальная сетевая передача (TCP/LiteNetLib вместо in-process) — не начата, `ITransport`
  специально спроектирован так, чтобы это был просто ещё один класс, а не переписывание.

## Текущее состояние: что реализовано

### Phase 1 (MVP) — полностью, и местами глубже плана

- Корабль: 5 комнат в ряд (кокпит/реакторная/коридор/каюты/машинное), двери — проёмы в общей
  стене, AABB-коллизии по осям (`Ship.MoveAlongAxis`).
- **Блочные стены корпуса**: у каждой комнаты периметр собран из блоков 1×1 (`WallBlock`), но
  только по **внешним** стенам корабля (где нет соседней комнаты) — внутренние переборки не
  бьются, там всё равно герметичный сосед, а не вакуум. Игрок при этом ходит свободно, не по
  тайлам — блочность только у стен.
- **Физика кислорода по Barotrauma**: у каждой комнаты `Oxygen` 0-100 (не флаг "пробит/цел").
  Каждая незаваренная пробоина тянет O2 вниз (-3/сек на пробоину). Генератор кислорода
  (физический блок-система "Кислород") качает O2 **только в свою комнату** (коридор), а дальше
  кислород **диффундирует через двери** к соседям пропорционально разнице уровней — дальние
  отсеки наполняются медленнее. Урон персонажу зависит от того, насколько упал O2 (порог 50,
  максимум урона при 0), а не от бинарного флага. Скафандр — полный иммунитет.
- **Множественные независимые пробоины**: враг пробивает случайный целый блок по всему кораблю
  (не "комнату целиком"), в одном отсеке может быть сразу несколько дыр, варится каждая отдельно
  ближайшая (F + держать сварочный аппарат в руке).
- **Инвентарь в стиле Barotrauma**: 9 слотов в ряд + 3 слота экипировки (наушники/одежда/головной
  убор, сейчас реально используется только "одежда" под скафандр). Полоска под слотом — клик
  мышью берёт/отпускает предмет из руки (`Inventory.ToggleHold`).
- **Механика рук**: у персонажа 2 "руки" (ёмкость, не отдельные слоты). Сварочный аппарат/
  автомат/лазерная винтовка — 2 руки, ключ/отвёртка/резак/нож — 1 рука. Взятие предмета,
  которому не хватает рук, автоматически "роняет" ранее взятые (Barotrauma-style).
- **Все предметы из дизайн-дока реализованы** как объекты (можно подобрать, держать в руке):
  AmmoCrate, Spacesuit, Wrench, Screwdriver, WeldingTool, Cutter, Knife, Rifle, LaserRifle,
  FuelRod. У ножа/автомата/лазерной винтовки **нет** геймплейного эффекта (рукопашная/стрельба
  личным оружием — Phase 3, абордаж), это осознанно.
- **Энергосеть, кликабельные блоки**: Реактор (большой блок, 4 слота под ядерные стержни —
  без стержня в хотя бы одном слоте нет выработки тока, даже если топливо есть) + Блок
  распределения (средний, рядом с реактором, слайдеры по 5 системам работают только пока блок
  открыт) + 5 обычных системных блоков (кислород/двигатель/щиты/орудия/прочее — можно
  повредить/починить ключом, у двигателя размер блока увеличен как у реактора). Все блоки —
  "заходишь" кликом левой кнопкой мыши, стоя рядом (радиус как у F-взаимодействия), автозакрытие
  при отходе.
- **Щиты**: общая полоса корабля (100 очков), заряжается только от мощности в слайдере "Щиты".
  Пока заряд > 0 — каждая атака врага поглощается щитом целиком, урон отсекам/турелям/системам не
  проходит вообще.
- Бой: 2 турели (баллистическая в кокпите, лазерная в реакторной — заряжается от слайдера
  "Орудия"), перископ с ограничением угла, боезапас+ящики патронов ИЛИ конденсатор.
- Враг: абстрактный HP, атакует по таймеру, конкурируют турель/система/блок стены, отступает
  <20% HP.
- **Карта галактики со свободной 2D-навигацией (Phase 2, milestone M8)**: заменила старую жёсткую
  цепочку "Transit→Battle→Station по таймеру". 6 фиксированных точек (`GalaxyMap.CreateStarter`),
  корабль стартует пристыкованным к домашней станции. Консоль навигации (кокпит) — кликабельный
  блок, открывает панель карты вместо вида корабля; клик по точке шлёт курс, корабль реально летит
  по прямой (скорость/дистанция имеют значение, не телепорт и не фиксированный таймер). Прибытие
  во враждебный сектор → бой (враг возрождается заново на каждую встречу через `EnemyShip.Reset()`);
  прибытие на станцию → дозаправка/заварка всех пробоин/восстановление кислорода. После победы —
  открытый космос, а не автовозврат на станцию: игрок сам решает, куда лететь дальше. Сменить курс
  посреди боя нельзя (сервер игнорирует).
- **Станционные NPC (Phase 2, milestone M9)**: консоль шлюза (`AirlockConsole`, коридор) —
  кликабельный блок, но открывается **только пока корабль пристыкован** (`Phase == Station`).
  `Station.CreateDefault()` — 2 NPC, одинаковый набор на любой станции пока (дифференциация по
  станциям — не сделана, later): Администратор (задания) и Торговец (снаряжение/ресурсы). Клик по
  NPC показывает статичный текст-заглушку диалога ("заданий пока нет" / "склад пуст") — реальных
  транзакций и заданий ещё нет, это база для M10 (экономика) и M11 (доставка груза). Полноценной
  ходьбы по станции (отдельная сцена/тайлмап станции) нет и не планировалась для этого milestone —
  сознательное упрощение против буквального текста дизайн-дока.

### Тесты

57/57 в `TestRunner.cs`. Все ключевые механики покрыты, включая пограничные случаи (несколько
пробоин в одной комнате, диффузия кислорода, нехватка рук, щиты поглощают первую атаку и т.д.).
8 подряд полных прогонов без единого падения (см. пункт 7 ниже про устранённую нестабильность).

## Известные грабли / уроки этой сессии

1. **Диагональное движение персонажа в тестах может промахнуться мимо двери.** Дверь — узкий
   проём (высота ~1.8 юнита) в общей стене; если двигаться по диагонали к цели с другим Y, чем
   спавн, есть шанс, что Y выйдет за пределы проёма как раз в момент пересечения X. В хелперах
   тестов (`MoveCharacterTo`) для перехода в другую комнату сначала идти горизонтально на той же
   высоте, что и текущая позиция (обычно Y=3, высота дверей), и только потом двигаться по
   вертикали внутри уже нужной комнаты.
2. **`ApplyCommand` не мёржит поля между вызовами.** Каждый `ClientCommand` перезаписывает
   `PowerSystemIndex`/`PowerDirection`/`MoveX`/`MoveY` и т.д. своими значениями (по умолчанию
   "ничего"). Если нужно одновременно двигать слайдер энергии И, например, лететь по карте —
   это **один** `ClientCommand` с обоими полями, а не два последовательных вызова (второй вызов
   без явного `PowerDirection` сбросит слайдер на 0 раньше, чем он успеет подействовать).
3. **Шрифт `DebugFont` не покрывает всю Unicode-пунктуацию.** `CharacterRegions` в
   `Content/DebugFont.spritefont` — это ASCII (0x20-0x7E) + кириллица (0x0400-0x04FF) + после
   этой сессии ещё общая пунктуация (0x2010-0x2027: тире, кавычки, многоточие). **Любой символ вне
   этих диапазонов в строке, которая реально уходит в `SpriteBatch.DrawString`, роняет всё
   приложение необработанным исключением** (`ArgumentException` в `SpriteFont.GetGlyphIndexOrDefault`)
   — это не "текст выглядит криво", это краш. Проверять новые строки интерфейса на такие символы;
   расширять `CharacterRegions` при необходимости (это XML, пересобирается автоматически через
   MonoGame Content Pipeline при `dotnet build`).
4. **Живая проверка через синтетические клики/клавиши в этой песочнице ненадёжна.** Между
   скриншотами окно игры может физически сместиться на экране (из-за самого чат-интерфейса), и
   заранее вычисленные координаты клика промахиваются — в т.ч. могут случайно попасть в чат и
   вписать туда мусорный текст (проверять и очищать поле ввода, **не отправляя** его, если это
   произошло). Также иногда встречается "утечка" глобального состояния клавиатуры/мыши между
   независимыми запусками процесса (персонаж или инвентарь оказываются в состоянии, которое
   вводом в текущей сессии не объяснить) — это артефакт песочницы, а не баг игры; если сомнения,
   проверять через автотесты (детерминированные), а не гоняться за визуальным подтверждением
   бесконечно.
5. Проект **не git-репозиторий** — нет возможности откатиться через git, будьте аккуратны с
   деструктивными операциями.
6. **Не гонять тяжёлую верификацию непропорционально задаче** (это в целом предпочтение
   пользователя): на маленькую правку — сборка+тесты достаточно, живой запуск клиента — когда
   есть заметный визуальный/интерактивный эффект.
7. **Долгий wait-луп перед измерением в тесте может сам "сжечь" измеряемую величину.** Было
   ~20% нестабильности в `World_Decompression_DrainsHealthInBreachedRoom` и
   `World_SuitedCharacter_ImmuneToDecompression`: измеряемый персонаж всё это время (поиск нужного
   состояния мира + "отстой" до нужного уровня кислорода, суммарно до 900 симулированных секунд)
   уже стоял в опасной комнате, и здоровье успевало упасть до 0 задолго до самого окна измерения
   before/after — тогда `after < before` ложно проваливалось, потому что оба замера читали уже
   "дно". Дело было не в недостаточных таймаутах (это чинили дважды до того, и всё равно ~20%
   флейка оставалось) — причина в том, что персонаж вообще не должен быть в опасности во время
   долгого поиска. **Фикс**: заводить/перемещать измеряемого персонажа в опасную комнату
   непосредственно **перед** самим окном измерения (1 секунда), а не держать его там всё время
   поиска нужного состояния мира. Проверено 8 подряд чистыми прогонами всего набора тестов.

## Дальше по плану — Phase 2 (см. `game_design.md` §12)

Согласованный с пользователем порядок (M8 и M9 сделаны, дальше M10→M14):

- **M10 — экономика (деньги)**: нужна как база для торговца и наград за задания.
- **M11 — задания на доставку груза**: взял ящик на одной станции → довёз целым на другую. Только
  доставка для начала (без добычи минералов — та требует ещё и открытого космоса с резаком,
  сознательно отложено на потом).
- **M12 — медик + упрощённые травмы**: предмет-аптечка + базовая механика ранений поверх текущего
  `Character.Health`.
- **M13 — прокачка корабля** у станционного механика, тратит деньги из M10.
- **M14 — кастомная прокладка проводов**: самое спекулятивное и трудоёмкое по объёму работы,
  сознательно оставлено последним.

Актуальный список задач синхронизирован в TaskCreate/TaskList на момент завершения этой сессии
(M1-M9 — completed, M10-M14 — pending) — если инструмент задач доступен на новой машине, свериться
с ним; если нет, ориентироваться на список выше.
